# forge

The mode `forge` builds a piece of work in slices that run side by side. It runs no command and uses no model of its own. It keeps a slice's tests in a database partition of its own while a builder works. It may be active in any project: a project that lists forge gets proof, git-worktrees and requirements with it, bound, and the toolchain is the project's own. Forge requires `requirements@1`: its workflow `design` reads a requirements file only through `requirements.check`, which answers with every problem and its line, or with the file's outcomes and conditions as data.

## What it does today

The action `waves` reads a plan file and works out, by script, what the owner reads before work starts:

```
bay call forge.waves '{"plan":"docs/plans/0022-forge-in-waves.yaml"}'
```

- **The table of slices**: each slice's name, title, kind, write scope, and the slices it comes after with the reason.
- **The waves**: slices in one wave have no order between them and scopes that share no path. Each wave can use one builder per slice. A slice goes in the first wave after every slice it comes after, and later still when its scope shares a path with a slice already in that wave.
- **The longest chain**, by names. The plan takes at least that many waves.
- **Every problem**, each with its sentence: an after that names no slice; a cycle, with the names in it; two slices that nothing orders whose scopes share a path, with the pattern of each and an example path; two such slices where forge cannot tell, with both patterns; a scope that admits every private file of a kernel feature, as a warning; a plan in which every slice waits for the one before and gives no reason in `oneAfterAnotherBecause`; a slice that changes a fixed file of a slice it does not come after. A plan that names its `requirements` is also checked for a condition no slice meets and a slice that meets a condition the file does not hold; one that names its `design`, for a slice with no interface file, one with a file the design did not commit, one that reaches two modules with no reason, and one of kind mode that meets no condition. `docs/plans/README.md` gives the form and each rule.

A file that is not YAML, or not in the form of a plan, is refused with every reason, each with its line. A slice with no write scope is refused this way, since `proof@1`'s slice requires one.

## One slice, from a plan's slice to the merge card

The workflow `one-slice` builds one slice of a plan:

```
bay call --workflow forge:workflows/one-slice.yaml '{"planned":{"title":"...","slice":{...}},"base":"<commit>","bugs":[]}'
```

It draws the start card from the slice and waits for the owner. The card shows the slice's title, kind, base, scope and afters; every item of its definition of done: its id, must or should, its sentence whole, how it is held, and what will be run or counted; then the bugs. In this workflow no planter runs: the card names the bugs to inject; with none named, it says which items that ask for bugs caught will not be known, or that none will be planted. The workflow `rounds` passes `planter: true` with the request to the step `slice`, and there the card says that the planter writes the bugs after the last round, or writes more after the bugs named. Each thing the card says is one line, and the kernel wraps it to 44 columns; forge breaks a word longer than 40 characters after a slash, or else where it must, so a long path wraps where it reads well. A word is never dropped, and a long card is never cut. Rejected, the run fails and nothing is cut. Approved, `worktrees.cut` makes `.forge/worktrees/<slice>` on `forge/<slice>`; the skill `declare` states the files and action names the builder will change, and `scripts/declared-in-scope.ts` sends back any file outside the write scope; the skill `build` writes the slice in the worktree, or stops with what is missing as a name. `worktrees.set-aside` commits the work to `forge/wip/<slice>/<n>`, `proof.prove` judges that commit, and `draw` turns proof's answer into the merge card, by the pure function in `scripts/lib/merge-card.ts`. The merge card is drawn as in the workflow `rounds` (below), with no rounds line, and the builder's lines cite the step `build`. Merge is offered only when the builder built the slice and every must item, `scope` and `declared` that proof judged passed; send-back is withheld, since no round runs after the card, and discard until slice WD1. Merge cuts `<slice>-merge` at the commit proof judged and merges it into the setting `into`, a branch nobody has checked out; keep leaves both branches. The build agent may write anywhere under `.forge/worktrees/`, not only in its own worktree: a write outside the slice is caught afterwards by proof's `scope` and `declared`, not stopped. Settings `into` and `practices` are the owner's to write.

## Rounds: a test writer, a builder who never has the tests, proof and a reviewer

The workflow `rounds` builds one slice under ADR 24, in at most three rounds:

```
bay call --workflow forge:workflows/rounds.yaml '{"planned":{"title":"...","slice":{...}},"base":"<commit>","bugs":[],"interface":["<path>"]}'
```

`interface` names the files the slice builds against, such as schema files; it may be left out. The steps are written out: `slice`, `start`, `begin`, `cut`, `pin`, `declare`, then `round-1`, `review-1`, `round-2`, `review-2`, `round-3`, `review-3`, then `bugs`, `prove` (the action `final-proof`), `draw`, `card` and `carry-out`. There is no loop. A round or a review with nothing to do passes on what it was given.

1. `slice` draws the start card and names the files the builder may not change: every test file the slice's `fails-first` items name. When the request names no interface files, the card says so under the scope: `interface: none named, so the test writer and the builder get no agreed shape`. The approval `start` then offers named choices in place of approve and reject. A slice that names interface files offers `build` and `stop`, and withholds `build-without-interface` with `The slice names its interface files.` A slice that names none offers `build-without-interface` and `stop`, and withholds `build` with `The slice names no interface files.` The kernel shows a withheld choice under Not available; it cannot hide one. `begin` ends the run on `stop`, with `The owner chose stop on the start card, so nothing is cut.`, and nothing is cut.
   In this workflow `slice` also hands on the slice as the final proof judges it: when no item of the plan's slice is of the kind `checks`, forge adds one, `checks`, must, whose sentence says forge added it since the plan lists none, so the toolchain's checks (types, lint, format and dead code for TypeScript) and its whole test run are asked of every slice (ADR 28, point 5). The rounds do not judge it; the final proof and the merge card do.
2. `worktrees.cut` makes `.forge/worktrees/<slice>` on `forge/<slice>`. The script `pin` then reads each interface file in that worktree, which is still the base, and records the toolbox's `shortHash` of its whole text, or no hash for a file the base does not hold. The skill `declare` states the builder's files; its check sends back a file outside the write scope, and a test file the slice names.
3. `round-1`, the script `round`: the skill `write-tests` (tier balanced, kept packed) writes the tests from the conditions and the interface, in the builder's worktree at its base, before any builder works. Its agent has no tool that writes a file; it hands its tests in as data, and `scripts/tests-handed-in.ts` checks them. Forge keeps them in its partition `kept-tests`, gzipped and in base64, each with a line at its top that holds the run's planted mark (below). The skill `build-without-tests` (tier balanced) writes the code; its task holds the slice, the interface's paths, the test files' paths and the declaration, never a line of a test. Forge commits the work, removes the builder's worktree and keeps its branch, cuts `<slice>-tests-1` at the builder's commit, runs the leak check (below) on the builder's changed files there, writes the tests there and commits them. That commit is the round's head. `proof.prove` judges it, with the slice less its `checks` items and no bugs; after a leak proof is not asked, and the round's state is done.
4. `review-n`, the script `review-round`, decides what follows a round:
   - The leak check found a leak: no model, and the rounds end. The builder is not sent round again.
   - The builder stopped: the rounds end.
   - A `must` item failed and this is round 1 or 2: no model. The builder's next round gets the failing cases, as below.
   - Otherwise the skill `review` (tier deep, kept packed, no tool that writes a file) judges the round. Its task holds the slice, the tests' text from the kept store, the builder's changed files as text, proof's verdicts, what the builder is told of the failing cases, the practices that review holds, and `skills/review/reviewing-tests.md`. It answers, for each condition, held by which cases or not held and why; for each practice given, by id, held, not-held with the path of a file the builder changed or of a test and one sentence on what is wrong there, or does-not-apply (ADR 28, point 6); and findings, each for the test writer or the builder, with the case's name, the question it fails and one sentence on the fix. Its check, `scripts/no-test-text.ts`, sends back a finding with no addressee, a field beyond the bounded ones, a fix or reason that is not one sentence, a finding for the builder or a reason that shares a run of 20 characters with a test, and a finding for the builder that names a case the tests do not name; a practice left out, answered twice or answered and not given, by the same check the design's and the plan's challengers get (`scripts/lib/practice-answers.ts`); and a practice not held with no path, with a path that is neither a changed file nor a test, with more than one sentence, or whose sentence about the builder's code shares a run of 20 characters with a test. The feedback quotes nothing of the tests. Every `review-n` that finds a round's worktree also records the hash of each interface file there, at the round's head, before it removes the worktree.
   - Findings for the builder go into the review's output. Findings for the test writer may quote the tests, so forge keeps them packed in its partition, and the output holds only their count. No finding, or round 3 reviewed, and the rounds end.
5. `round-2` and `round-3` run only when the review before asks for them. With findings for the test writer, forge cuts `<slice>-writer-n` at the base, which holds no builder's work; `write-tests` gets its earlier tests and its findings, and forge removes that worktree and its branch once the tests are handed in. With findings for the builder, or failing cases, forge cuts `<slice>-n` at the builder's last commit; `build-without-tests` gets its findings and the failing cases there. Then a new head, `<slice>-tests-n`, and proof, as in round 1.
6. `bugs`, the script `bugs`, runs once. When the slice has a `bugs-caught` item, the builder built it and no leak was found, forge cuts `<slice>-planter` at the builder's last commit, reads the builder's changed files there, less the test files, and asks the skill `plant` (tier balanced). The planter's task holds the conditions, the interface's paths and that code as text: no folder, no test, no test's text. It answers with at most ten bugs in the shape `proof.prove` takes. Its check, `scripts/bugs-in-the-code.ts`, reads the kept tests and sends back a bug that changes no file, a test file or a file the builder did not change, that names a test file no `fails-first` item names, or whose name or added lines share a run of 20 characters with a test; bugs that share a name; and more than ten. The feedback names bugs by number and quotes nothing. Forge then removes the worktree and keeps its branch, since the worktrees interface deletes only a branch merged into the checked-out one. Its output is the bugs for proof, the owner's first, then the planter's, at most 50, a name used twice made distinct with ` (2)`, ` (3)`; and how many the planter wrote.
7. `prove`, the action `final-proof` (marked `calledOutputs: kept-packed`, with a script limit of 1,800 seconds), asks `proof.prove` to judge the last head with the slice whole and those bugs. The kernel keeps that call, proof's answer and every step under it packed. The script compares proof's answer with the kept tests while they still exist: a failing case's message that shares a run of 20 characters with a test is emptied, and a detail or reason that does is replaced by `Proof's reason is kept from the card: it quotes a test.` Its own output, which the kernel keeps as text, is that filtered answer in proof@1's form. The filter fails closed: when the final proof finds no kept tests for the slice, because none were kept or a replay of the step comes after they were forgotten, every failing case's message is emptied and every detail and reason is replaced, so the card shows names only. The round's filter of the failing cases and `review-round`'s carrying of a fix do the same: with no kept tests, every message is withheld and counted, and every fix is kept from the card. Then it forgets the kept tests and the mark with them, in every run, planter or not, leak or not, and also when proof's call failed. `draw` draws the merge card; only a `must` item's verdict, a stopped builder, a leak, a must practice the reviewer answered not held and an interface file that changed during the rounds withhold merge. The card leads with the answer: `Merge is offered: every must item that proof judged passed.`, or `Merge is not offered:` and why. Then a computed line for each leak: `leak: <file> shares <n> lines with the tests`, `leak: <file> holds the mark planted in the tests`, or `leak: the builder's answer holds the mark planted in the tests`. No line is drawn when no leak was found, and none says there was none. Then each item of done, and `scope` and `declared`: its id, must or should, passed, failed, not known or for you to judge, and its sentence. Under a failed or not known item, `why:` and proof's reason in forge's words for the sentences proof writes, or a general sentence for any other; then `proof's reason:` and proof's own detail or reason, control characters shown as spaces, cut at 240 characters. In the workflow `rounds` that is the filtered text above. Under a failed `checks` or `fails-first` item, its failing cases from proof's answer: at most three names, control characters shown as spaces, cut at 120 characters, each followed in the workflow `rounds` by `its message:` and the message the filter left, when one is left; then how many more, those the toolchain did not list counted in; then how many test files did not load. The workflow `one-slice` shows no case's message, since nothing compared it with the tests. Under a passed `checks` item, the checks and the count of tests. Then the practices (ADR 28, point 7), from the last review, as `scripts/lib/practices-block.ts` draws them: one computed line, `practices answered by the reviewer in round <n>: <count>; <h> held, <m> not held, <k> do not apply; a check holds <t> more`, where the last count is the rows of the practices files a check, the compiler or the linter holds and review does not; then each practice not held as a judged line citing that review step, `<id>, must, not held: <its sentence, cut at 80 characters> In <path>: <the reviewer's sentence>`, with `must` only for an id in `mustPractices`, and `kept from the card: it quotes a test` in place of a sentence that shares a run of 20 characters with the tests. When the rounds ended with no review, one line says `practices: not judged, since the rounds ended with no review`. The tally line and the not-held lines are drawn by the same code as the design and plan cards'. Then where the work is, its size, the files the kernel, an adapter, a kit schema or a base manifest changed; for a slice with interface files, the hashes `pin` recorded compared with those of the last head: one line per file that changed, appeared, is gone or could not be compared, each of which withholds merge and is named in the reason, or one line `interface files: <n> unchanged since the base, by hash`; then how many bugs the planter wrote and each bug that survived with its files. Then the rounds: how many ran of at most three, and why they ended: `a leak ended them`, `the builder stopped`, `the reviewer had no findings` or `no more may run`. A computed line, `the reviewer, in round <n>, before the final proof:`, says when the reviewer's lines below it were judged, so a condition the reviewer held does not read as a contradiction of proof's final verdict. The reviewer's verdicts and the findings that remain, at most three named, are judged lines that cite the review step under which the reviewer last ran. A finding for the builder reads `for the builder, <question>: <fix>`; one for the test writer reads `for the test writer, <question>, <case>: <fix>`. A fix is carried from the review step, where the kept tests still exist, only when it shares no run of 20 characters with them; otherwise the line ends `kept from the card: it quotes a test`. What the builder says is missing when it stopped, and each of its `decisions`, at most three of at most 120 characters, are judged lines that cite the round under which it last built; the kernel adds the skills and tiers of that step, which are the test writer's and the builder's when both ran in it. A withheld choice's reason is a full sentence. Send-back and discard are withheld: no round runs after the card.

What a failing case tells the builder (ADR 24, item 5, which allows names and messages):

- The failed `must` items' ids.
- Each failing case's name as the test runner gives it, control characters shown as spaces, cut at 200 characters. A name is the test writer's sentence for the case; its skill says that a name and an assertion's message hold no value of the test.
- The case's file only when it is one of the slice's named test files. Its path is already in the builder's task as `fixed`, so it tells nothing more.
- The message only when it shares no run of 20 characters with any of the slice's tests, compared with the tests' text, character by character. Otherwise the name alone, and a count of messages withheld.
- A test file that did not load: its path, when the slice names it, and nothing of its content.

Who can read what, in every round:

| While | On disk under `.forge/worktrees/` | In the step's task |
|---|---|---|
| the test writer, round 1 | the builder's worktree at the base, no work yet | conditions, interface, folder |
| the test writer, rounds 2 and 3 | its own worktree at the base only | its earlier tests, conditions, interface, its findings |
| the builder, any round | its own worktree, its own work; no test file | conditions, interface, test paths, its findings, the filtered failing cases |
| proof | the round's tests worktree: work and tests | |
| the reviewer | the round's tests worktree: work and tests | tests, code, verdicts, failing cases, practices |
| the planter | `<slice>-planter` at the builder's last commit: work, no test file | conditions, interface, code; not the folder |

The kernel keeps the test writer's and the reviewer's tasks and answers packed in `.agentbay/kernel.db`. Forge's partition holds the tests packed until the step `prove` has filtered proof's answer against them, then deletes them: the worktrees interface cannot read a file at a commit without a worktree on disk while a builder works.

The leak check (ADR 27, item 4) runs after each round's build, in `scripts/lib/leak-check.ts`, by the pure rule in `scripts/lib/leaks.ts`. Code and its tests rightly share imports, names, paths and the conditions' words, so the check compares whole lines, not runs of 20 characters. Each line is trimmed and its spaces collapsed. A line of a test counts when, after taking out web addresses, the conditions' sentences, the scope's start and the paths both sides were given (the builder's files, the test files and the interface files), with case ignored, at least 40 characters that are not spaces remain, and it is not an import line. Such a line is a leak in a file the builder changed when the file holds the same line, unless the line stands in an interface file or in that same file at the slice's base; forge cuts `<slice>-base-<n>` at the base to read them only when some line would count, and removes it and its branch after. Each file is named once, with the count of distinct lines it shares. The second half is a mark: when forge first keeps a run's tests it draws 32 random hex characters with `node:crypto`, and puts them as a line at the top of each kept test, in the partition only. Every reader of the kept tests gets them without that line: the tests worktree, the reviewer, a later test writer and the planter's check. A builder's changed file, or its answer, that holds the mark is a leak. The rounds' state records each leak by the builder's path, kind and count, never a line of a test and never the mark. The check finds copied text and the mark; it cannot show that a builder never read a test: one that read a test and wrote its own code from it passes. It misses a copied line cut or joined with another, a line under 40 characters once the given words are out, a file past the 200 the code reader hands on, and a test file the builder wrote, which the tests overwrite. The mark is only in forge's partition: the test writer's answer, which the kernel keeps packed in `.agentbay/kernel.db`, does not carry it, so a builder that read that answer and copied a line is caught only by the shared-text rule. It can cry wolf for a long line both sides wrote alone, such as a long shared constant in a new file; the owner then reads the named file and chooses keep. Forge rewrites the kept tests only when they change, so a round the kernel replays keeps its mark; a run that failed and left identical rows behind reuses their mark.

What forge holds, with the hook or without it: no test is a file while a builder's step is open; the builder's task holds no line of a test; the test writer's task and its folder hold no line of the builder's code; the builder has no tool that runs a command, and the test writer and the reviewer none that writes a file.

What forge does not hold:

- The final proof's answer is kept packed, and its filtered form is text. A round's own output, the rounds' state, is text too: it holds proof's verdicts without their cases, each detail or reason that quotes a test replaced, and the failing cases as the builder is told them. The filter finds a shared run of 20 characters; it misses a test's text reworded or cut shorter.
- The card does not say whether skill steps ran with the hook, and no line on it says the steps were confined: a script cannot read its run's events, so it cannot know.
- A `scope` or `declared` verdict that proof did not give does not withhold merge. The proof mode always gives both; a stand-in may not.
- A write outside the declared files is not stopped. Proof's items `scope` and `declared` find it afterwards.
- The round script has the kernel's limit of 480 seconds, and proof's run is inside it. The final proof's script has 1,800 seconds, the kernel's most, and proof's own step the same, so proof's planned 1,740 seconds fit inside it with a minute left. A slice whose named tests take longer to run on the base and the head fails the run. A longer limit adds a warning to `bay check`, which the kit's tests pin; that is the owner's call.
- A run that fails between the first test writer and the last review leaves the slice's rows in the partition.

After a run the branches `forge/<slice>`, `forge/<slice>-n` and `forge/<slice>-tests-n` stay, and no worktree of the rounds is on disk.

## Design: from a requirements file to the interfaces later slices build against

```
bay call --workflow forge:workflows/design.yaml '{"file":"docs/requirements/todo.yaml"}'
```

The steps: `read` (`requirements.check`), `start`, the approval `path`, `designs`, `challenge`, `draw`, the approval `card`, `commit`.

1. `start` (`scripts/design-start.ts`) ends the run on a refused file with one sentence that names every problem and its line, so nothing is designed. Otherwise it draws the first card: the file, its version and who signed it, each outcome with its count of conditions, and what each path costs: light, one designer and a challenger, 2 calls at tier deep, up to 6 when checks send them back; full, two designers who write apart and a challenger who compares them, 3 calls, up to 9. The choices are `light`, `full` and `stop`.
2. `designs` (`scripts/designs.ts`) ends the run on `stop`. It asks the skill `design` (tier deep) once, or twice on the full path, each with the requirements and a stance set by script; the second designer's task holds nothing of the first design. The action `design` keeps its output packed (`skillOutput: kept-packed`), so while the second designer works the first design is in no file and in `.agentbay/kernel.db` only gzipped. `designs` itself does not pack its calls, so a design that fails its check in the last round ends the run with the check's sentences. The designer hands in the design as data in `schemas/design.json`.
3. The design's check, `scripts/design-checked.ts`, by the pure rules in `scripts/lib/design-rules.ts`, names every problem at once: a name used twice; a module with no interface; a module that implements an interface the design does not define; an interface no module implements; a table or a file two modules own; a condition no action serves; an action that serves a condition the requirements do not have; an action that serves none and gives no reason in `because`; an action with no worked example; a refusal with no words; an example whose earlier call names an action its interface does not have; a schema whose `$ref` names anything but a part of itself or another schema file of its interface; a schema file that would be written outside `docs/designs/<job>/`; a module or interface named utils, helpers, common, manager or the like (P-36). Then `scripts/lib/design-examples.ts` holds every worked example to its action's schemas, as below. A design that breaks a rule goes back to its designer, at most three rounds.
4. `challenge` (`scripts/challenge-designs.ts`) lists where two designs differ, by `scripts/lib/design-compare.ts`: modules, interfaces and actions in one only, a module's interfaces or ownings, request and response schemas, and which actions serve each condition. It reads the practices held by design (rows whose holder starts with `design`: P-32, P-35 and P-52 in the kit) from the setting `practices` in a worktree `<job>-practices` cut at the setting `into`, and asks the skill `challenge` (tier deep). Its check, `scripts/challenge-checked.ts`, sends back an answer that leaves a practice out, answers one twice or one not given, chooses second or merged with one design, chooses merged with no design or gives a design with first or second, or gives a merged design that is not in the form of `schemas/design.json` or breaks a rule of the design check.
5. `draw` (`scripts/lib/design-card.ts`) draws the design card: the answer, which design, which path, and whether approve is offered; the requirements' counts; each module, what it implements and owns, and what it hides as a judged line citing the designers' step, or the challenger's for a merged design; each interface and one line for each action with the conditions it serves and its count of examples; coverage; how many rules the script checked and every problem; the count of examples and what of them was checked against their actions' schemas, naming the input of each refusal, which is not checked; the practices the script's rules hold (P-35, P-36, P-38, P-42); the challenger's counts and each practice it answered not held as a judged line; on the full path where the two designs differed and why the challenger chose. Approve is withheld while the check finds a problem or a practice held by design is answered not held.
6. `commit` (`scripts/commit-design.ts`) ends the run on `stop`. On approve it cuts `<job>-design` at `into`, writes `docs/designs/<job>/design.yaml` (the design as JSON, which is YAML, with each schema named by its path) and `docs/designs/<job>/schemas/<interface>/<action>-request.json` and `-response.json`, commits them with `worktrees.commit`, merges with `worktrees.merge`, and removes the worktree, keeping its branch. Its output names the commit, the merge commit, `into`, the design file and, as `interface`, every file written, in the form the workflow `rounds` takes.

Each worked example is held to its action's schemas by `context.schemas.checkAgainst`: the input and the answer of an example that answers, and the input of each earlier call against the request schema of the action it calls. A schema that names another file of its interface is checked with that file's schema in its `$defs`. A refusal's input is not checked, since the design does not say whether the schema or the action refuses it; its sentence must have words. A schema the kernel refuses (too large, a reference outside the interface, not a schema) is a problem of its own, naming the action and the side. What it does not hold: an answer's truth beyond its shape. A run that fails while the challenger works leaves the worktree `<job>-practices`. The branches `forge/<job>-practices` and `forge/<job>-design` stay after the run (WB1). The leak check counts every string of the interface files at the slice's base, a design's worked examples among them, as words both sides were given.

## Plan: from a committed design to a plan whose first wave can start

```
bay call --workflow forge:workflows/plan.yaml '{"design":"docs/designs/todo/design.yaml"}'
```

The steps: `start`, `plan-1`, `challenge-1`, `plan-2`, `challenge-2`, `draw`, the approval `card`, `commit`. No step repeats.

1. `start` (`scripts/plan-start.ts`) cuts `<job>-plan-reading` at the setting `into`, reads the design file and the practices held by a plan (rows whose holder is `plan`: P-33, P-34 and P-35 in the kit), removes the worktree, and checks the requirements file the design names with `requirements.check`. A refused file ends the run with every problem and its line, by the same code as the design's first step.
2. `plan-1` is the skill `plan` (tier balanced). The planner hands in a plan as data in `schemas/plan.json`. Its check, `scripts/plan-checked.ts`, sets `requirements` and `design` from the run and sends back every error `forge.waves` would name, at most three rounds.
3. `challenge-1` is the skill `challenge-plan` (tier deep, another model than the planner, P-27). It answers each practice held by a plan, held, not-held or does-not-apply with a sentence, and gives findings. Its check, `scripts/plan-challenge-checked.ts`, is the design challenger's check of the answers by practice.
4. `plan-2` (`scripts/plan-again.ts`) asks the planner again with its first plan and the findings, only when there are findings. `challenge-2` (`scripts/challenge-again.ts`) asks the challenger to read the answer, only when the planner was asked.
5. `draw` (`scripts/lib/plan-card.ts`) draws the plan card: the answer first, how many slices in how many waves, the longest chain, and whether approve is offered; each wave with its slices, each with its module, its title cut to 60 characters and the conditions it meets; the afters; coverage; whether every fixed file is made first; what the script checked and each problem; the practices the script's rules hold and the challenger's counts, each not held as a judged line; the findings left after the planner's answer as judged lines; and what the planner changed, worked out by script. Approve is withheld while the check finds an error or a practice held by a plan is answered not held.
6. `commit` (`scripts/commit-plan.ts`) ends the run on `stop`. On approve it cuts `<job>-plan` at `into`, writes `docs/plans/<number>-<job>.yaml` with the next free four-digit number in that folder, commits, merges and removes the worktree, keeping its branch. Its output names the commit, the merge commit, `into`, the plan file, and as `wave` the slice request of each slice of the first wave, in the form the workflow `rounds` takes, with the plan's commit as `base`.

What it does not hold: `forge.waves` reads the design from the project's folder, the workflow from `into`. The branches `forge/<job>-plan-reading` and `forge/<job>-plan` stay after the run (WB1), so a second plan of one job is cut only after they are deleted. The design's version of the requirements is not compared with the file's version now.

## The plan's form

`schemas/plan.json`: a title, and a list of slices, each a title and a slice, with the optional fields `docs/plans/README.md` gives. The slice is `proof@1`'s slice, held by reference to `proof@1/prove-request.json#/$defs/slice`, so the two cannot drift. That is why forge requires `proof@1`, and why the kit's config binds `proof`.

Whether two scopes share a path is one pure function, `scripts/lib/scopes.ts`. It matches paths with the toolbox's `pathMatch`, the matching `proof@1`'s kind `in-scope` uses, and it confirms every example path with it. A pattern `pathMatch` refuses is never answered "share no path".

## Settings

`into`: the branch a merge goes into. `practices`: the practices files a builder reads, relative to the project.

`mustPractices`: the ids of the practices the workflow `rounds` treats as must, such as `P-12`. While the reviewer's last answer says one of them is not held, the merge card withholds merge and names it; keep stays. Left out, none: a practice not held is shown on the card and withholds nothing. The kit sets P-12, P-52, TS-17, TS-21 and TS-25. The workflows `design` and `plan` do not read it: there every practice held by design or by a plan withholds approve when the challenger answers it not held.

`featureMap`: the project's map of features, such as `framework/features.yaml`. Forge reads each feature's private files from it for the warning on a whole feature. Left out, no scope is compared with a feature. The kit sets it.
