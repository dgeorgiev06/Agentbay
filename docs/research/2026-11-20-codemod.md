## Answer in brief

1. Codemod ships YAML workflows today (CLI 1.18.7, `latest` on npm). Nodes form a graph with `depends_on`, a matrix fans a node out, a manual trigger pauses it, and shared state carries values. The live docs show only this form.
2. The code-first form, `workflow.ts`, is alpha (`2.0.0-alpha.4`, 19 November, npm tag `alpha`), on an unmerged branch. A TypeScript function calls `step()`. Each step's result is recorded. A resume replays finished steps by label and content. `Promise.all` is the fan-out. YAML is translated into the same TypeScript.
3. In the alpha, workflow state is gone: each step returns a value, and the next step takes it as an ordinary variable. Agentbay's `$steps.<id>.output` is the same idea, held by the kernel instead of by a language.
4. Agentbay should keep YAML. The kernel never drives a model, and cards cite step ids. A deterministic TypeScript body needs a sandboxed runtime and a build step that agentbay does not have and does not need. Three small additions close the gaps: steps side by side with a cap, `$trigger` with a path, and a bounded repeat whose inner steps a card can cite.
5. Codemod's agent support has three parts. AST transforms (jssg, ast-grep) do the certain part. An `agent` or `ai` step hands the rest to a coding agent, with full autonomy by default. CI checks on the pull request judge the result, and campaigns can auto-heal failures. Nothing like proof's script verdicts, hidden tests or planted bugs exists. Forge is ahead on verification. Codemod is ahead on scale: sharding, campaigns, one pull request per shard.
6. Worth taking: siblings that finish and are recorded when one fails; replay-safe clock and random for scripts; `given` and `until` for workflow tests; a confinement table per harness; publishing from a verified source for the mode index. Not worth taking: approvals that bind no content, approve-all flags, a handed-off agent step that counts as succeeded, and auto-heal without the owner.

## 1. What a Codemod workflow is today

**Shipped, YAML (`main:docs/community/workflows/reference.mdx`).** The author writes `workflow.yaml` with `version`, `params`, `state`, `templates` and `nodes`. A node has an id, a type (`automatic` or `manual`), `depends_on`, an optional `strategy` and ordered `steps`. Step kinds: `js-ast-grep` (jssg), `ai`, `install-skill`, `ast-grep`, `codemod` (a registry package), `run` (shell) and `shard`. Each step may have `if`, `env` and, in cloud runs, `commit`. The engine schedules nodes as a graph, refuses cycles, and runs each node's steps in order as a task.

- Values flow through declared shared state. A shell step writes key-value lines to a state output file, with an append form for arrays. A jssg transform calls `setState`. `${{ state.x }}` works in some fields and not in others, and step outputs are not wired into expressions (same file, "Variable Resolution").
- Fan-out: a node with `strategy: matrix` and `from_state` spawns one parallel task per array item. Removing an item marks its task `WontDo`. A master task tracks the rest.
- Human gate: `trigger: { type: manual }` holds a node in `AwaitingTrigger`. `codemod workflow resume -i <run> --trigger-all` or `-t <task>` releases it.
- Resume: tasks and state are persisted per run; resume picks up paused or failed tasks.
- Validation (`main:docs/community/cli.mdx`): parsing against the spec, unique ids, existing and acyclic `depends_on`, template references, and that every matrix has values or `from_state`. The docs say plainly that it cannot check logic or runtime behaviour.
- Testing: `codemod jssg test` runs one transform over `input`/`expected` fixture pairs. Before the alpha, a whole workflow had no test runner.

**Alpha, TypeScript (`engine/code-first:docs/community/workflows.mdx`, `engine/code-first:docs/community/workflows/reference.mdx`).** The author writes `workflow.ts`, whose default export is an async function. It receives `params`, `target` and `dryRun`, and it calls `step(label, task, options)`. Tasks: `forEachFile` with an inline callback or with `jssg(path)` or `astGrep(path)`; `shell`; `agent`; `codemod`; `installSkill`; `shard`; `dependencyGraph`; `approval`; `sleep`; `waitForEvent`; `branch`, `commit` and `pullRequest`. The alpha's type file exports the same set (`npm-alpha4/package/types/modules/workflow.d.ts`).

- What runs: the body runs in a QuickJS context. A build step (oxc) pulls each callback and each function step into its own isolate, passes outside variables in as frozen JSON copies, and reports scope breaches as build errors with line and column (`engine/code-first:crates/workflow/README.md`, "Layout").
- The body must be deterministic. Importing `fs`, `child_process`, timers or `codemod/llm` in the body is a build error naming the import chain. `Date` and `Math.random` in the body are replay-safe: the random generator is seeded by the run, and the clock moves only when a step finishes (reference, "The workflow body").
- Resume: every step's result is saved when it finishes. `codemod workflow resume --id` replays finished steps whose label and content match and runs the rest. Editing a step makes it run again, so a run can be fixed by editing the workflow (reference, "How a workflow runs").
- A step has `retries`, `retryDelay` and `timeout`. Changing these does not count as changing the step.
- Fan-out: a step starts when `step()` is called, so `Promise.all` runs steps side by side. `forEachFile` runs per file in parallel and commits all changes together after conflict checks. A callback that fails on some files leaves the step `partial`; the rest is applied. When one step fails, the steps started beside it finish and are recorded before the run ends (reference, "Runs").
- Human gate: `approval(message)` asks in a terminal. With `--no-interactive` the run pauses and exits successfully; `resume --approve` continues; `run --approve` approves everything up front. The approval task carries only the message (`engine/code-first:crates/workflow/src/tasks/approval.rs`).
- Events: `waitForEvent(name)` waits for `codemod workflow send <name> --id <run> --data`. An event sent early is kept.
- Validation: `codemod workflow validate -w workflow.ts` builds the workflow and reports the callback rules. `tsc` checks types, so a step result that is not JSON is a type error.
- Testing (`engine/code-first:docs/community/workflows/testing.mdx`): `codemod/testing` gives `runWorkflow`, `fixtures` and `assertTree`. A test runs the whole workflow on a temporary copy of a fixture and compares the resulting tree. `given` replaces a named step's result, and `until` stops after a named step. Approvals are given by default, agent steps must be given, and the CLI's sandboxed runtime can be chosen with `host: "quickjs"`.
- YAML still runs. It is translated into the same TypeScript, and `codemod workflow upgrade` converts a package for good (`engine/code-first:docs/community/workflows/migrate.mdx`). The YAML engine's own orchestration was removed on the branch (commit `0608783`, 12 November).

**Shipped versus alpha.** npm has `latest` 1.18.7 (10 November) and `alpha` 2.0.0-alpha.1 to alpha.4 (13 to 19 November), from `https://registry.npmjs.org/codemod`. The live reference page shows YAML with shared state and no TypeScript. The engine's README lists what is not done yet, including crash-safe file commits and conflict checks between steps running in parallel.

## 2. Why state was removed, and how it compares with `$steps.<id>.output`

The record of the reason is thin. The handoff notes quote a maintainer's rule that state must go away completely and that the migration assistant must not use state or metrics (`st:HANDOFF.md`, "Goal"). No decision record gives a deeper reason. What the docs and code show is the effect:

- A jssg transform returns `{ edit, data }`. The step's `data` is a list of each file's data by path, or one value folded by a reducer.
- A shell step returns `stdout`, `stderr` and `exitCode`.
- A function step or callback returns its value.
- `getState`, `setState`, the lock and the step-output functions are build errors that name the replacement (reference, "Values between steps").
- Translated YAML keeps state as a plain object local to the run. Shell steps still read and write it, and the generated workflow, not the engine, copies the lines back (`engine/code-first:crates/core/README.md`). On Windows this path fails before any step runs (`migrate.mdx`).

My reading of why: shared state let any step write any key, so a replay could not know which steps a value depended on. Return values make the dependency visible in the code, and they are saved with the step that made them.

Agentbay's form is the same idea. A step's output is saved under its id; a later step names it with `$steps.<id>.output` and a path; nothing is shared or mutable (`schemas/workflow.schema.json`, `bay/runs/workflow-steps.ts`). The load check refuses a reference to a step that is not earlier (`bay/manifests/references.ts`).

What is clearer in Codemod's form:

- Types flow from the task to the variable, so a wrong field is a compile error. In agentbay a path into an output is a string. I did not find a check of that path against the output schema at load.
- A test can give a step's result by name and stop after a step.

What is safer in agentbay's form:

- Every value has a schema at both ends, the action's input and output.
- A reference cannot run code.
- An approval is bound to the hash of what it shows.

## 3. Code-first or YAML

**What Codemod gains with `workflow.ts`:**

- Ordinary control flow: `if`, loops and `Promise.all` in place of `depends_on`, `if:` strings and matrix nodes.
- Typed values between steps, inline per-file callbacks, and imports of npm packages.
- A test runner for the whole workflow, and a fix made by editing the workflow, replayed by label and content.

**What it pays:**

- A sandboxed JavaScript runtime with isolates, and a build that extracts callbacks and checks scope.
- Rules an author must learn: no reassigned outer variables, callbacks written inline, and impure modules banned from the body.
- Translation code kept for old YAML, with the Windows gap above.
- A workflow that is no longer data. A script cannot list its steps without building and inspecting it; the README names an `inspect` function for that.

**For agentbay, stay with YAML.** The reasons:

- The kernel never drives a model, and a workflow's steps are what the owner's cards cite by id.
- `bay check` reads a workflow as data, and the schema closes the set of step kinds.
- Forge already moves logic into scripts, a round being one script step (`components/base/forge/workflows/rounds.yaml`, `docs/designs/forge-whole/A.md` section 4). That is where code-first logic belongs in agentbay.

The gaps can be closed in Codemod's spirit, where a value comes from a step and is saved with it:

- **Steps side by side, for WV1.** A `foreach` that may run its items side by side, with a required cap. Its output is the list of item outputs in item order. When an item fails, the items already started finish and are recorded, and the step fails, naming every failed item. This mirrors Codemod's rule that siblings finish and are recorded. It also matches the earlier Specter note's point that a wave reports every slice's failure.
- **A field of the trigger.** `$trigger.<path>`, resolved like `$steps.<id>.output.<path>`. Codemod's `params` object does this. The reference parser already splits paths for steps (`bay/manifests/references.ts`), so this is the same rule applied to one more root.
- **A bounded repeat, for rounds.** A `repeat` step with a required `at-most` and an `until` that names an inner step's output. Inner steps are keyed by the repeat number, and their keys stay visible to `quotes`, so a card can cite review 2. Codemod has no such step: a TypeScript loop does it. ADR 26 already names a counted repeat as the fallback. Design A found that a `foreach`'s inner keys are not kept outside it (`A.md`, "Why rounds need no kernel change"); a repeat must fix that or the card cannot cite rounds.

## 4. Codemod agents

**Names found, and where:**

- `agent` task, workflow.ts (`engine/code-first` reference, "Coding agents").
- `ai` step, YAML (`main` reference, "AI Step"), run by a Rig-based harness (`engine/code-first:docs/community/workflows/ai-harness-rig.mdx`).
- Codemod MCP, local: `npx codemod mcp` (`main:docs/community/model-context-protocol.mdx`).
- Platform MCP, hosted at `app.codemod.com/api/v1/mcp` (`main:docs/enterprise/codemod-mcp.mdx`, September changelog).
- Codemod Agent, formerly Codemod Wish (`main:docs/enterprise/codemod-agent.mdx`).
- Campaigns, with sharding, AI review, CI recovery and auto-heal (`main:docs/enterprise/campaigns.mdx`).
- Automations, with a Coding Agent action (`main:docs/enterprise/automations.mdx`).
- Skills `codemod` and `sdk-migration` (`main:skills/`).
- jssg, the JavaScript ast-grep transform runtime (`main:docs/community/jssg.mdx`).

Web searches for these names returned mostly mirror sites. The current names above come from the repository's own docs.

**How model steps and deterministic transforms are combined.** The docs' complete example orders the steps this way: a registry codemod, then a jssg transform for project patterns, then an AI step for the hard cases, then ast-grep cleanup rules, then a formatter (`main` reference, "Complete Example"). The shipped skill tells an agent to search the registry first, prefer deterministic codemods to open rewrites, and dry-run before applying (`main:skills/codemod/SKILL.md`, its description). The `sdk-migration` skill sorts each breaking change into three buckets: automatable now, automatable later, or manual. It requires fixtures for each automatable change, and it says to fix and retest until green (`main:skills/sdk-migration/SKILL.md`).

**What the model is trusted to do.** `agent()` runs an installed coding agent with `autonomy: "full"` by default, so it edits files and runs commands without asking. `"read-only"` is offered. For each of 18 agents the docs say whether read-only holds, holds only by the agent's defaults, or cannot hold; a read-only step naming an agent that cannot hold fails before it starts (reference, "Coding agents"). When the run was itself started by a coding agent, the step hands the prompt back to that agent and succeeds with `handedOff: true` (same section, and `ai-harness-rig.mdx`). The built-in harness has bash, an edit tool, glob, a code-graph tool and others, and it compacts context with bounded retries (`ai-harness-rig.mdx`).

**What is checked after.** Within a workflow, only the steps the author adds after the agent step. In campaigns, CI checks on each pull request. Auto-heal can patch a pull request, or repair and republish a codemod package when a failure looks systematic, up to a retry cap (`campaigns.mdx`). The hosted MCP requires approval, by MCP elicitation, for creating a campaign or indexing a repository. It says itself that a confirmation is not a permission boundary (`codemod-mcp.mdx`, "Approvals").

**How large migrations are split and tracked.** `shard` groups the files a dry run of the transform would change, by directory or code owner, or by a custom function. Re-running it with `previous` keeps earlier assignments and puts new files in new shards (`engine/code-first:docs/community/workflows/sharding.mdx`). A campaign runs one task per shard, each on its own branch with its own pull request. It shows a graph and a table of tasks, lets a failed task be re-run, and syncs status with Jira.

**What an agent is given.** The local MCP has four tools: dump an AST, list node types, run jssg tests, and validate a package. It also serves about ten guidance resources. The hosted MCP covers Insights, Grep, the registry, campaigns and automations. `npx codemod ai` installs a master skill and the MCP for the user's agent (`model-context-protocol.mdx`).

**Against forge.** Forge's practice P-32 says a step that needs no judgement is a script. Codemod's ordering is close in spirit: deterministic transform first, model for the remainder. The difference is in verification.

- Codemod trusts the agent's edit and leaves judgement to fixtures the author wrote, to later steps, or to CI.
- Forge never lets the party that wrote the code judge it. Proof gives verdicts by script, the test writer is apart from a builder who never has the tests, a planter plants bugs, the leak check runs, and the merge card marks each line as ran, computed or judged (ADR 24, ADR 27, `components/base/forge/README.md`).
- Codemod has nothing like hidden tests, planted bugs or line marks.
- Forge has nothing like shards or one pull request per shard.

## 5. Packages and registry against the mode index and `bay install`

**Codemod's package model** (`engine/code-first:docs/community/package-structure.mdx`, `main:docs/community/publishing.mdx`):

- `codemod.yaml` holds name, version, author, licence, `workflow` or a list of named `workflows` with one default, target languages, keywords, registry access and visibility, and declared capabilities (`fs`, `fetch`, `child_process`).
- A package may be workflow-only, skill-only or both. Skills live under `agents/skill/<name>/` with required frontmatter.
- `codemod publish` validates the package's shape.
- Publishing works by interactive login, API key, or trusted publishers: GitHub Actions OIDC, restricted by repository, workflow, environment or ref, with tokens of about five minutes.
- Release channels are dist-tags (`latest`, a builder preview tag, SemVer prereleases) (`main:docs/changelog.mdx`, August).
- Registry metadata is offered to AI tools as `/llms.txt` and `/ai-catalog.json` (September changelog).
- Interactive runs can approve elevated capabilities at runtime (August changelog).

**Agentbay's plan.** A mode index with `bay install` comes after 5.0.0 (`docs/proposals/0022-typescript-port.md`, line 256), with signed modes in the index for public use (same file, line 188). Trust is bound to the hash of a mode's list (`CONTEXT.md`, Trust).

**Comparison:**

- Codemod's capabilities are three coarse words, approved per run. Agentbay's list names each command with its words and effects, and trust is re-asked when the list changes. Agentbay's model is stricter and should stay.
- Codemod's publishing provenance is ahead. A package can be tied to the repository and workflow that built it, with no long-lived secret.
- Named workflow variants with one default fit agentbay already: a mode lists several workflows.

## 6. What each lacks

**Codemod does, agentbay lacks:**

- Steps side by side, with siblings recorded on a failure.
- Replay-safe clock and random in the deterministic part.
- A workflow test runner with `given` and `until`.
- Events sent to a waiting run.
- Sharding with stable reassignment.
- A table of what each harness can confine.
- Trusted publishing.
- Per-step retries and timeouts.

**Agentbay does, Codemod lacks:**

- Approvals bound to the hash of what is shown, and choices with rules.
- Cards whose lines carry a mark and a checked source.
- Budgets in dollars, tokens, items and minutes.
- Proof by script, with a closed set of kinds.
- Hidden tests, planted bugs and the leak check.
- Effects and grants per action, and trust bound to a list's hash.
- A kernel that drives no model.
- Skill outputs checked by scripts before they are accepted.

**A mistake to take:**

- The TypeScript body.
- Content-free approvals, and approve-all flags.
- Counting a handed-off agent step as succeeded.
- Full autonomy as the default.
- Repair and republish without the owner.

## Ideas worth taking

1. **Siblings finish and are recorded when one fails.** When steps run side by side and one fails, let the rest finish, record them, then fail the step and name every failure. A resume runs only the failed ones.
   - Lands: kernel workflows; forge WV1.
   - Smallest form: `foreach` gains `side-by-side: <cap>`. The output stays a list in item order. The failure names each failed item.
   - Cost or risk: concurrency in the engine. Budget draws from many branches at once. Two builders need per-run folders (design B's WR1, still undesigned). The card must cite inner steps.

2. **A bounded repeat whose rounds a card can cite.** Replace the unrolled `round-1` to `review-3` with one step that runs its inner steps at most N times until an output says stop.
   - Lands: kernel workflows; forge rounds; PL1's challenge and answer; DS1.
   - Smallest form: `repeat: { at-most: 3, until: $steps.<inner-id>.output.<path> }`. Inner keys carry the round number and stay visible to `quotes`.
   - Cost or risk: a kernel change, and the card's citation rule must learn inner keys. `at-most` must be required and small, or runs grow without bound.

3. **`$trigger` with a path.** Let a step take one field of the starting input, as it can of a step's output.
   - Lands: kernel workflows; every forge workflow, which today passes the whole request through a first script step.
   - Smallest form: the same path rule as for `$steps`, applied to `$trigger`.
   - Cost or risk: very small. Without a trigger schema the path cannot be checked at load; add an optional input schema per workflow if wanted.

4. **A replay-safe clock and random for scripts.** A forge script runs again from its start on resume, so anything random or timed must be stored (plan 0024, "After LK1"). Codemod seeds the run's random and moves its clock only when a step finishes.
   - Lands: kernel toolbox; forge scripts such as the leak check's mark.
   - Smallest form: `toolbox.random(bytes)` and `toolbox.now()`, recorded per call and replayed on resume. A lint rule refuses `node:crypto` random calls and `Date.now` in mode scripts.
   - Cost or risk: small. The lint rule has to know which modules count as mode scripts.

5. **`given` and `until` in the test toolbox.** Give a named step's output without running it, and stop after a named step, so one step of a workflow can be tested alone.
   - Lands: `tests/test-toolbox.ts`; forge's workflow tests; DS1 and PL1 tests.
   - Smallest form: two options on the call that runs a workflow, keyed by step id. A given output is checked against that action's output schema.
   - Cost or risk: a given output that skips its schema would test nothing real, so the check is required.

6. **A confinement table per harness.** Each harness adapter states whether it can run a step with no shell, with no write tool, and with reads confined. A step that needs one the harness cannot give fails before it starts, and the card names the harness.
   - Lands: adapters; cards; the Codex adapter (5.2).
   - Smallest form: a fixed record in each adapter, read by `bay check` and by the kernel when it hands out a task.
   - Cost or risk: little while only Claude Code exists. The table must be tested against the harness, not written from its docs.

7. **Publishing from a verified source, for the mode index.** An index entry records the repository, workflow and ref that built it, proved by a short-lived OIDC token. A version, once published, never changes.
   - Lands: the mode index and `bay install`, after 5.0.0.
   - Smallest form: an index entry holds the source, the commit and the hash of the mode's list. `bay install` shows them on the trust card.
   - Cost or risk: ties the index to one CI provider at first. Provenance says where a mode came from, not that it is safe; trust stays the owner's.

## Not worth taking

- **The code-first body.** It needs a deterministic sandboxed runtime, a build that extracts callbacks, and rules an author must learn. Agentbay keeps logic in scripts and the workflow as data that cards cite and `bay check` reads.
- **Replay by label and content, so that editing a workflow fixes a run.** In agentbay an approval is bound to what it showed. A run whose steps change under it would make the owner's earlier answers mean something else.
- **An approval that carries only a message, `--approve` up front, and approvals given by default in tests.** Each weakens the rule that an approval is the owner's and bound to content (P-28).
- **An agent step that succeeds when it hands its prompt back to the parent agent.** It records work as done when none was done. Agentbay's sighting rule exists to refuse exactly that.
- **Full autonomy as the default for agent steps.** Forge's builder has no command tool on purpose (ADR 27).
- **Auto-heal that republishes a package when CI fails.** It changes shipped work with no card. A failure should come back to the owner as a card, with a send-back choice.
- **A step marked partial when some files failed.** Forge merges a slice whole or not at all. Partial success would blur the merge card's answer.
- **Shared state in any form.** Both projects have dropped it.
- **Handlebars templates in automations.** A second expression language beside references.

## What I could not verify

- Nothing was run. Every claim about alpha behaviour rests on docs, types and code read on `engine/code-first`.
- Whether `2.0.0-alpha.4` holds exactly the branch I read. Its types have no `getState` and do have shell `stdout`, so it includes the state removal. I did not compare the rest.
- The reason for removing state. Only the handoff note's quoted rule exists. I found no decision record. The reading in section 2 is mine.
- PR numbers and their states come from `st:HANDOFF.md`. The GitHub API was not available in this session.
- The hosted features (campaigns, auto-heal, Codemod Agent, automations, the platform MCP) are closed source. I read their docs only.
- Live docs: I fetched two pages, and both show YAML only. Other pages were read from the repository's `docs/` folder, which may differ from what is served.
- Whether agentbay checks a reference's path against the earlier step's output schema at load. I saw only the check that the step is earlier.
- Whether Codemod enforces that a published version never changes. The docs say not to reuse one; I found no enforcement.
