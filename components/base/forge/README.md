# forge

The mode `forge` builds a piece of work in slices that run side by side. It runs no command and uses no model of its own. It keeps a slice's tests in a database partition of its own while a builder works. It may be active in any project: a project that lists forge gets proof, git-worktrees and requirements with it, bound, and the toolchain is the project's own. Forge requires `requirements@1`: its workflow `design` reads a requirements file only through `requirements.check`, which answers with every problem and its line, or with the file's outcomes and conditions as data.

Each skill step in `mode.yaml` names its role in place of a tier, and runs at the tier the kit gives that role in `bay/roles.ts` (ADR 29). Below, each skill is named with its role and tier.

## What it does today

The action `waves` reads a plan file and works out, by script, what the owner reads before work starts:

```
bay call forge.waves '{"plan":"docs/plans/0022-forge-in-waves.yaml"}'
```

- **The table of slices**: each slice's name, title, kind, write scope, and the slices it comes after with the reason.
- **The waves**: slices in one wave have no order between them and scopes that share no path. Each wave can use one builder per slice. A slice goes in the first wave after every slice it comes after, and later still when its scope shares a path with a slice already in that wave.
- **The longest chain**, by names. The plan takes at least that many waves.
- **Every problem**, each with its sentence: an after that names no slice; a cycle, with the names in it; two slices that nothing orders whose scopes share a path, with the pattern of each and an example path; two such slices where forge cannot tell, with both patterns; a scope that admits every private file of a kernel feature, as a warning; a plan in which every slice waits for the one before and gives no reason in `oneAfterAnotherBecause`; a slice that changes a fixed file of a slice it does not come after. A plan that names its `requirements` is also checked for a condition no slice meets and a slice that meets a condition the file does not hold; one that names its `design`, for a slice with no interface file, one with a file the design did not commit, one that reaches two modules with no reason, and one of kind mode that meets no condition. `docs/plans/README.md` gives the form and each rule.

A file that is not YAML, or not in the form of a plan, is refused with every reason, each with its line. A slice with no write scope is refused this way, since `proof@1`'s slice requires one.

## One slice, from a plan's slice to the merge card

The workflow `one-slice` builds one slice of a plan:

```
bay call --workflow forge:workflows/one-slice.yaml '{"planned":{"title":"...","slice":{...}},"base":"<commit>","bugs":[]}'
```

It draws the start card from the slice and waits for the owner. The card shows the slice's title, kind, base, scope and afters; every item of its definition of done: its id, must or should, its sentence whole, how it is held, and what will be run or counted; then the bugs. In this workflow no planter runs: the card names the bugs to inject; with none named, it says which items that ask for bugs caught will not be known, or that none will be planted. The workflow `rounds` passes `planter: true` with the request to the step `slice`, and there the card says that the planter writes the bugs after the last round, or writes more after the bugs named. Each thing the card says is one line, and the kernel wraps it to 44 columns; forge breaks a word longer than 40 characters after a slash, or else where it must, so a long path wraps where it reads well. A word is never dropped, and a long card is never cut. Rejected, the run fails and nothing is cut. Approved, `worktrees.cut` makes `.forge/worktrees/<slice>` on `forge/<slice>`; the skill `declare` (the builder, tier balanced) states the files and action names the builder will change, and `scripts/declared-in-scope.ts` sends back any file outside the write scope; the skill `build` (the builder, tier balanced) writes the slice in the worktree, given the slice's rules, empty when its request carries none, or stops with what is missing as a name. `worktrees.set-aside` commits the work to `forge/wip/<slice>/<n>`, `proof.prove` judges that commit, and `draw` turns proof's answer into the merge card, by the pure function in `scripts/lib/merge-card.ts`. The merge card is drawn as in the workflow `rounds` (below), with no rounds line, and the builder's lines cite the step `build`. Merge is offered only when the builder built the slice and every must item, `scope` and `declared` that proof judged passed; send-back is withheld, since no round runs after the card, and discard until slice WD1. Merge cuts `<slice>-merge` at the commit proof judged and merges it into the setting `into`, a branch nobody has checked out, then removes that worktree and the slice's and drops the three branches; keep leaves both branches and the slice's worktree. The build agent may write anywhere under `.forge/worktrees/`, not only in its own worktree: a write outside the slice is caught afterwards by proof's `scope` and `declared`, not stopped. Settings `into` and `practices` are the owner's to write.

## Rounds: a test writer, a builder who never has the tests, proof and a reviewer

The workflow `rounds` builds one slice under ADR 24, in at most three rounds:

```
bay call --workflow forge:workflows/rounds.yaml '{"planned":{"title":"...","slice":{...}},"base":"<commit>","bugs":[],"interface":["<path>"]}'
```

`interface` names the files the slice builds against, such as schema files; it may be left out. The steps are written out: `look`, `slice`, `start`, `begin`, `cut`, `pin`, `declare`, then `round-1`, `review-1`, `round-2`, `review-2`, `round-3`, `review-3`, then `bugs`, `prove` (the action `final-proof`), `draw`, `card` and `carry-out`. There is no loop. A round or a review with nothing to do passes on what it was given.

1. `slice` draws the start card and names the files the builder may not change: every test file the slice's `fails-first` items name. When the request names no interface files, the card says so under the scope: `interface: none named, so the test writer and the builder get no agreed shape`. The approval `start` then offers named choices in place of approve and reject. A slice that names interface files offers `build` and `stop`, and withholds `build-without-interface` with `The slice names its interface files.` A slice that names none offers `build-without-interface` and `stop`, and withholds `build` with `The slice names no interface files.` The kernel shows a withheld choice under Not available; it cannot hide one. `begin` ends the run on `stop`, with `The owner chose stop on the start card, so nothing is cut.`, and nothing is cut.
   Before it, `look` (the action `leftovers`) asks for each branch an earlier run of the slice may have left with work in it, `forge/<slice>`, `forge/<slice>-<n>` and `forge/<slice>-tests-<n>` for each of the three rounds, where it points, by asking `worktrees.find-branch`, which changes nothing and answers its commit or that it is not there. A branch that exists is a line of the start card, `an earlier run left <branch> at <commit>`, followed by `building over drops them and gives each commit in full, so their work can be found again`. The go-ahead then offered is `build-over`, or `build-over-without-interface` for a slice that names no interface files; `build` and `build-without-interface` are withheld with `An earlier run left branches of this slice; build over them or stop.` With no such branch, both are withheld with `No earlier run left a branch of this slice.` Exactly one go-ahead is offered, beside `stop`. On a build over, `begin` sets aside and removes a worktree such a branch still has, drops the branches, and answers each with its commit; a drop worktrees refuses ends the run with its reason before anything is cut. Nothing is dropped on `stop`.
   In this workflow `slice` also hands on the slice as the final proof judges it: when no item of the plan's slice is of the kind `checks`, forge adds one, `checks`, must, whose sentence says forge added it since the plan lists none, so the toolchain's checks (types, lint, format and dead code for TypeScript) and its whole test run are asked of every slice (ADR 28, point 5). The rounds do not judge it; the final proof and the merge card do.
2. `worktrees.cut` makes `.forge/worktrees/<slice>` on `forge/<slice>`. The script `pin` then reads each interface file in that worktree, which is still the base, and records the toolbox's `shortHash` of its whole text, or no hash for a file the base does not hold. The skill `declare` (the builder, tier balanced) states the builder's files; its check sends back a file outside the write scope, and a test file the slice names.
3. `round-1`, the script `round`: the skill `write-tests` (the test writer, tier balanced, kept packed) writes the tests from the conditions and the interface, in the builder's worktree at its base, before any builder works. Its agent has no tool that writes a file; it hands its tests in as data, and `scripts/tests-handed-in.ts` checks them. Forge keeps them in its partition `kept-tests`, gzipped and in base64, each with a line at its top that holds the run's planted mark (below). The skill `build-without-tests` (the builder, tier balanced) writes the code; its task holds the slice, the interface's paths, the slice's rules, empty when its request carries none, the test files' paths and the declaration, never a line of a test. The test writer is given the same rules and tests them through each action's entry, choosing its cases by what a rule takes and gives; the builder writes each as a pure function named in camelCase after the rule, with the thin function around it. Forge commits the work, removes the builder's worktree and keeps its branch, cuts `<slice>-tests-1` at the builder's commit, runs the leak check (below) on the builder's changed files there, writes the tests there and commits them. That commit is the round's head. `proof.prove` judges it, with the slice less its `checks` items and no bugs; after a leak proof is not asked, and the round's state is done.
4. `review-n`, the script `review-round`, decides what follows a round:
   - The leak check found a leak: no model, and the rounds end. The builder is not sent round again.
   - The builder stopped: the rounds end.
   - A `must` item failed and this is round 1 or 2: no model. The builder's next round gets the failing cases, as below.
   - Otherwise the skill `review` (the reviewer, tier deep, kept packed, no tool that writes a file) judges the round. Its task holds the slice, the tests' text from the kept store, the builder's changed files as text, proof's verdicts, what the builder is told of the failing cases, the practices that review holds, the slice's rules, empty when its request carries none, by which it answers P-52, and `skills/review/reviewing-tests.md`. It answers, for each condition, held by which cases or not held and why; for each practice given, by id, held, not-held with the path of a file the builder changed or of a test and one sentence on what is wrong there, or does-not-apply (ADR 28, point 6); and findings, each for the test writer or the builder, with the case's name, the question it fails and one sentence on the fix. Its check, `scripts/no-test-text.ts`, sends back a finding with no addressee, a field beyond the bounded ones, a fix or reason that is not one sentence, a finding for the builder or a reason that shares a run of 20 characters with a test, and a finding for the builder that names a case the tests do not name; a practice left out, answered twice or answered and not given, by the same check the design's and the plan's challengers get (`scripts/lib/practice-answers.ts`); and a practice not held with no path, with a path that is neither a changed file nor a test, with more than one sentence, or whose sentence about the builder's code shares a run of 20 characters with a test. The feedback quotes nothing of the tests. Every `review-n` that finds a round's worktree also records the hash of each interface file there, at the round's head, before it removes the worktree.
   - Findings for the builder go into the review's output. Findings for the test writer may quote the tests, so forge keeps them packed in its partition, and the output holds only their count. No finding, or round 3 reviewed, and the rounds end.
5. `round-2` and `round-3` run only when the review before asks for them. With findings for the test writer, forge cuts `<slice>-writer-n` at the base, which holds no builder's work; `write-tests` gets its earlier tests and its findings, and forge removes that worktree, keeping its branch, and drops the branch once the tests are handed in. With findings for the builder, or failing cases, forge cuts `<slice>-n` at the builder's last commit; `build-without-tests` gets its findings and the failing cases there. Then a new head, `<slice>-tests-n`, and proof, as in round 1.
6. `bugs`, the script `bugs`, runs once. When the slice has a `bugs-caught` item, the builder built it and no leak was found, forge cuts `<slice>-planter` at the builder's last commit, reads the builder's changed files there, less the test files, and asks the skill `plant` (the planter, tier balanced). The planter's task holds the conditions, the interface's paths and that code as text: no folder, no test, no test's text. It answers with at most ten bugs in the shape `proof.prove` takes. Its check, `scripts/bugs-in-the-code.ts`, reads the kept tests and sends back a bug that changes no file, a test file or a file the builder did not change, that names a test file no `fails-first` item names, or whose name or added lines share a run of 20 characters with a test; bugs that share a name; and more than ten. The feedback names bugs by number and quotes nothing. Forge then removes the worktree, keeping its branch, and drops the branch. Its output is the bugs for proof, the owner's first, then the planter's, at most 50, a name used twice made distinct with ` (2)`, ` (3)`; and how many the planter wrote.
7. `prove`, the action `final-proof` (marked `calledOutputs: kept-packed`, with a script limit of 1,800 seconds), asks `proof.prove` to judge the last head with the slice whole and those bugs. The kernel keeps that call, proof's answer and every step under it packed. The script compares proof's answer with the kept tests while they still exist: a failing case's message that shares a run of 20 characters with a test is emptied, and a detail or reason that does is replaced by `Proof's reason is kept from the card: it quotes a test.` Its own output, which the kernel keeps as text, is that filtered answer in proof@1's form. The filter fails closed: when the final proof finds no kept tests for the slice, because none were kept or a replay of the step comes after they were forgotten, every failing case's message is emptied and every detail and reason is replaced, so the card shows names only. The round's filter of the failing cases and `review-round`'s carrying of a fix do the same: with no kept tests, every message is withheld and counted, and every fix is kept from the card. Then it forgets the kept tests and the mark with them, in every run, planter or not, leak or not, and also when proof's call failed. `draw` draws the merge card; only a `must` item's verdict, a stopped builder, a leak, a must practice the reviewer answered not held and an interface file that changed during the rounds withhold merge. The card leads with the answer: `Merge is offered: every must item that proof judged passed.`, or `Merge is not offered:` and why. Then a computed line for each leak: `leak: <file> shares <n> lines with the tests`, `leak: <file> holds the mark planted in the tests`, or `leak: the builder's answer holds the mark planted in the tests`. No line is drawn when no leak was found, and none says there was none. Then each item of done, and `scope` and `declared`: its id, must or should, passed, failed, not known or for you to judge, and its sentence. Under a failed or not known item, `why:` and proof's reason in forge's words for the sentences proof writes, or a general sentence for any other; then `proof's reason:` and proof's own detail or reason, control characters shown as spaces, cut at 240 characters. In the workflow `rounds` that is the filtered text above. Under a failed `checks` or `fails-first` item, its failing cases from proof's answer: at most three names, control characters shown as spaces, cut at 120 characters, each followed in the workflow `rounds` by `its message:` and the message the filter left, when one is left; then how many more, those the toolchain did not list counted in; then how many test files did not load. The workflow `one-slice` shows no case's message, since nothing compared it with the tests. Under a passed `checks` item, the checks and the count of tests. Then the practices (ADR 28, point 7), from the last review, as `scripts/lib/practices-block.ts` draws them: one computed line, `practices answered by the reviewer in round <n>: <count>; <h> held, <m> not held, <k> do not apply; a check holds <t> more`, where the last count is the rows of the practices files a check, the compiler or the linter holds and review does not; then each practice not held as a judged line citing that review step, `<id>, must, not held: <its sentence, cut at 80 characters> In <path>: <the reviewer's sentence>`, with `must` only for an id in `mustPractices`, and `kept from the card: it quotes a test` in place of a sentence that shares a run of 20 characters with the tests. When the rounds ended with no review, one line says `practices: not judged, since the rounds ended with no review`. The tally line and the not-held lines are drawn by the same code as the design and plan cards'. Then where the work is, its size, the files the kernel, an adapter, a kit schema or a base manifest changed; for a slice with interface files, the hashes `pin` recorded compared with those of the last head: one line per file that changed, appeared, is gone or could not be compared, each of which withholds merge and is named in the reason, or one line `interface files: <n> unchanged since the base, by hash`; then how many bugs the planter wrote and each bug that survived with its files. Then the rounds: how many ran of at most three, and why they ended: `a leak ended them`, `the builder stopped`, `the reviewer had no findings` or `no more may run`. A computed line, `the reviewer, in round <n>, before the final proof:`, says when the reviewer's lines below it were judged, so a condition the reviewer held does not read as a contradiction of proof's final verdict. The reviewer's verdicts and the findings that remain, at most three named, are judged lines that cite the review step under which the reviewer last ran. A finding for the builder reads `for the builder, <question>: <fix>`; one for the test writer reads `for the test writer, <question>, <case>: <fix>`. A fix is carried from the review step, where the kept tests still exist, only when it shares no run of 20 characters with them; otherwise the line ends `kept from the card: it quotes a test`. What the builder says is missing when it stopped, and each of its `decisions`, at most three of at most 120 characters, are judged lines that cite the round under which it last built; the kernel adds the skills and tiers of that step, which are the test writer's and the builder's when both ran in it. A withheld choice's reason is a full sentence. Send-back and discard are withheld: no round runs after the card.

What a failing case tells the builder (ADR 24, item 5, which allows names and messages):

- The failed `must` items' ids.
- Each failing case's name as the test runner gives it, control characters shown as spaces, cut at 200 characters. A name is the test writer's sentence for the case; its skill says that a name and an assertion's message hold no value of the test.
- The case's file only when it is one of the slice's named test files. Its path is already in the builder's task as `fixed`, so it tells nothing more.
- The message only when it shares no run of 20 characters with any of the slice's tests, compared with the tests' text, character by character. Otherwise the name alone, and a count of messages withheld.
- A test file that did not load: its path, when the slice names it, and nothing of its content.

Who can read what, in every round:

| While | On disk under `.forge/worktrees/` | In the step's task |
|---|---|---|
| the test writer, round 1 | the builder's worktree at the base, no work yet | conditions, interface, folder |
| the test writer, rounds 2 and 3 | its own worktree at the base only | its earlier tests, conditions, interface, its findings |
| the builder, any round | its own worktree, its own work; no test file | conditions, interface, test paths, its findings, the filtered failing cases |
| proof | the round's tests worktree: work and tests | |
| the reviewer | the round's tests worktree: work and tests | tests, code, verdicts, failing cases, practices |
| the planter | `<slice>-planter` at the builder's last commit: work, no test file | conditions, interface, code; not the folder |

The kernel keeps the test writer's and the reviewer's tasks and answers packed in `.agentbay/kernel.db`. Forge's partition holds the tests packed until the step `prove` has filtered proof's answer against them, then deletes them: the worktrees interface cannot read a file at a commit without a worktree on disk while a builder works.

The leak check (ADR 27, item 4) runs after each round's build, in `scripts/lib/leak-check.ts`, by the pure rule in `scripts/lib/leaks.ts`. Code and its tests rightly share imports, names, paths and the conditions' words, so the check compares whole lines, not runs of 20 characters. Each line is trimmed and its spaces collapsed. A line of a test counts when, after taking out web addresses, the conditions' sentences, the scope's start and the paths both sides were given (the builder's files, the test files and the interface files), with case ignored, at least 40 characters that are not spaces remain, and it is not an import line. Such a line is a leak in a file the builder changed when the file holds the same line, unless the line stands in an interface file or in that same file at the slice's base; forge cuts `<slice>-base-<n>` at the base to read them only when some line would count, and removes it and drops its branch after. Each file is named once, with the count of distinct lines it shares. The second half is a mark: when forge first keeps a run's tests it draws 32 random hex characters with `node:crypto`, and puts them as a line at the top of each kept test, in the partition only. Every reader of the kept tests gets them without that line: the tests worktree, the reviewer, a later test writer and the planter's check. A builder's changed file, or its answer, that holds the mark is a leak. The rounds' state records each leak by the builder's path, kind and count, never a line of a test and never the mark. The check finds copied text and the mark; it cannot show that a builder never read a test: one that read a test and wrote its own code from it passes. It misses a copied line cut or joined with another, a line under 40 characters once the given words are out, a file past the 200 the code reader hands on, and a test file the builder wrote, which the tests overwrite. The mark is only in forge's partition: the test writer's answer, which the kernel keeps packed in `.agentbay/kernel.db`, does not carry it, so a builder that read that answer and copied a line is caught only by the shared-text rule. It can cry wolf for a long line both sides wrote alone, such as a long shared constant in a new file; the owner then reads the named file and chooses keep. Forge rewrites the kept tests only when they change, so a round the kernel replays keeps its mark; a run that failed and left identical rows behind reuses their mark.

What forge holds, with the hook or without it: no test is a file while a builder's step is open; the builder's task holds no line of a test; the test writer's task and its folder hold no line of the builder's code; the builder has no tool that runs a command, and the test writer and the reviewer none that writes a file.

What forge does not hold:

- The final proof's answer is kept packed, and its filtered form is text. A round's own output, the rounds' state, is text too: it holds proof's verdicts without their cases, each detail or reason that quotes a test replaced, and the failing cases as the builder is told them. The filter finds a shared run of 20 characters; it misses a test's text reworded or cut shorter.
- The card does not say whether skill steps ran with the hook, and no line on it says the steps were confined: a script cannot read its run's events, so it cannot know.
- A `scope` or `declared` verdict that proof did not give does not withhold merge. The proof mode always gives both; a stand-in may not.
- A write outside the declared files is not stopped. Proof's items `scope` and `declared` find it afterwards.
- The round script has the kernel's limit of 480 seconds, and proof's run is inside it. The final proof's script has 1,800 seconds, the kernel's most, and proof's own step the same, so proof's planned 1,740 seconds fit inside it with a minute left. A slice whose named tests take longer to run on the base and the head fails the run. A longer limit adds a warning to `bay check`, which the kit's tests pin; that is the owner's call.
- A run that fails between the first test writer and the last review leaves the slice's rows in the partition.

Which branches an ending keeps and drops is one pure rule, `branchesAfter` in `scripts/lib/branch-endings.ts`, used by the rounds, the design, the plan and the wave; the scripts drop through `scripts/lib/drops.ts`, which always names `into`, so the integration branch is never dropped, and drops a branch only after its worktree is removed with the branch kept. A drop is safe to repeat: a branch that is not there is an answer. A worktree forge cuts only to read or write in, the writer's, the leak check's base, the planter's, the merge's, the practices', the plan reading's, a wave's joins and its readings, goes with its branch as soon as it is removed, and a leftover of the same name from a run that ended early is removed and dropped before the cut. When the rounds end, in the `review-n` that ends them, every earlier builder branch and tests branch is dropped: only the builder's last branch and the last tests branch stay, the two the merge card names, `the work and the tests are on <tests branch>, the builder's work alone on <builder branch>`. Merge drops those two and the merge branch once the work is in `into`; keep leaves the two. A drop that worktrees refuses never fails a run: the step's answer names the branch under `stayed` with worktrees' sentence, and a card that follows has the line `<branch> stayed: <the sentence>`. A run that fails or is stopped leaves what it made; the next run's start card names what may hold work, and forge's own scratch is dropped at its next cut. No worktree of the rounds is on disk after an ending.

## Design: from a requirements file to the interfaces later slices build against

```
bay call --workflow forge:workflows/design.yaml '{"file":"docs/requirements/todo.yaml"}'
```

The steps: `read` (`requirements.check`), `start`, the approval `path`, `designs`, `challenge`, `design-again`, `challenge-again`, `draw`, the approval `card`, `commit`. No step repeats.

1. `start` (`scripts/design-start.ts`) ends the run on a refused file with one sentence that names every problem and its line, so nothing is designed. Otherwise it draws the first card: the file, its version and who signed it, each outcome with its count of conditions, and what each path costs: light, one designer and a challenger, 2 calls at tier deep, 4 when the designer answers the challenger once, up to 12 when checks send them back; full, two designers who write apart and a challenger who compares them, 3 calls, 5 with the answer, up to 15. The choices are `light`, `full` and `stop`.
2. `designs` (`scripts/designs.ts`) ends the run on `stop`. It reads the practices held by design (rows whose holder starts with `design`: P-32, P-35 and P-52 in the kit) from the setting `practices` at the head of the setting `into`, through `read-on-branch` in a worktree `<job>-practices` that is removed before any designer works, so a replay reads the same texts. It asks the skill `design` (the designer, tier deep) once, or twice on the full path, each with the requirements, a stance set by script and those practices, by id and words; the second designer's task holds nothing of the first design. A designer says in `practices` of its design, in one sentence per practice, how the design holds it or why it does not apply; forge does not write those sentences into the design's files. The action `design` keeps its output packed (`skillOutput: kept-packed`), so while the second designer works the first design is in no file and in `.agentbay/kernel.db` only gzipped. `designs` itself does not pack its calls, so a design that fails its check in the last round ends the run with the check's sentences. The designer hands in the design as data in `schemas/design.json`.
3. The design's check, `scripts/design-checked.ts`, by the pure rules in `scripts/lib/design-rules.ts`, names every problem at once: a name used twice; a module with no interface; a module that implements an interface the design does not define; an interface no module implements; a table or a file two modules own; a condition no action serves; an action that serves a condition the requirements do not have; an action that serves none and gives no reason in `because`; an action with no worked example; a refusal with no words; an example whose earlier call names an action its interface does not have; a schema whose `$ref` names anything but a part of itself or another schema file of its interface; a schema file that would be written outside `docs/designs/<job>/`; a module or interface named utils, helpers, common, manager or the like (P-36); a long text said by rule that cannot be spelled out (below). Then `scripts/lib/rules-applied.ts` holds the design's rules (`docs/designs/forge/rules-in-a-design.md`): a module lists `rules`, each a pure function with its name, what it decides, what it takes and what it gives, each value with its schema and, for a value read from or written to a table or file of the module, its `store`; an action names the `rule` it applies, and in `reads` and `writes` what its thin function reads before and writes after. The check names an action that writes or refuses in an example and applies no rule; a rule the design does not have; a rule held by a module that does not offer the action's interface; a table or file an action reads or writes, or a rule stores in, that its module does not own; a table or file the action writes that its rule does not give, one the rule gives that the action does not write, one the rule takes that the action does not read, and one the action reads that its rule does not take; a rule no action applies; two rules, or two values of one side of a rule, of one name; a table or file a module owns that no action reads or writes; a rule's schema whose `$ref` names anything but a part of itself or `schemas/<interface>/<action>-<side>.json` of an interface its module implements; a rule that takes no unstored value though its action's request has fields, or gives none though its action has a response; a value with an empty schema; an example that comes after calls the design's examples refuse and answers otherwise than an example that makes the same calls without them, since a refused call writes nothing; and a request or response schema with a field named `$text`, which an example could not tell from a long text said by rule. Each check is counted alone, and the card's count is the number of checks the script ran. The challenger is told what the script cannot see: a value whose schema says little, an optional stored field the thin function could choose by, a time or a random value read inside a rule, and an action that filters with no rule. A store, an action's `reads` and `writes`, is a path of letters, digits, dots, dashes, underscores and slashes; the card shows one cut at 80 characters, and quoted if it is anything else. Then `scripts/lib/design-examples.ts` holds every worked example to its action's schemas, as below. The same check sends back a design that leaves out a practice it was given, answers one not given or answers one twice (not counted among the rules). A design that breaks a rule goes back to its designer, at most three rounds; the run then ends undone. Undone rolls nothing back: no design was committed, and the kernel says undone because `designs` read the practices in a worktree it removed, a delete the kernel counts and does not undo. A run stopped on the design card ends the same way.
4. `challenge` (`scripts/challenge-designs.ts`) lists where two designs differ, by `scripts/lib/design-compare.ts`: modules, rules, interfaces and actions in one only, a module's interfaces or ownings, a rule kept in another module or what it takes, gives or decides, the rule an action applies and what it reads or writes, request and response schemas, and which actions serve each condition. It asks the skill `challenge` (the challenger, tier deep) with the practices the designers were given. The challenger answers each practice and may give findings that are not a practice's answer, at most 10, each what is wrong, where in the design and what would fix it. Its check, `scripts/challenge-checked.ts`, sends back an answer that leaves a practice out, answers one twice or one not given, chooses second or merged with one design, chooses merged with no design or gives a design with first or second, or gives a merged design that is not in the form of `schemas/design.json` or breaks a rule of the design check.
5. `design-again` (`scripts/design-again.ts`) asks the designer of the chosen design to answer the first challenge once, only when it answered a practice not held or gave a finding: the same skill `design`, with its stance, the practices, and in `answering` the chosen design, each practice not held with its sentence and the findings. On the full path that is the designer of the design chosen; a merged design goes to the designer of the first stance, who then sees in it the other designer's work. `challenge-again` (`scripts/challenge-design-again.ts`) asks the challenger to judge the answered design once more, only when the designer was asked: one design, no differences, and in `answered` what the first challenge answered not held and found, and `changes`: what the answer changed from the chosen design, as `answerChanges` in `scripts/lib/design-compare.ts` lists it, never the chosen design itself. The second challenge's answers decide the card; when the designer was not asked, the first's do. The rule of when to ask is one pure function, `secondPassNeeded` in `scripts/lib/second-round.ts`; both steps ask through `askedWhenNeeded` there, which the plan's second round uses too through `onlyWhenNeeded` in `scripts/lib/plan-sources.ts`. `scripts/lib/second-round.ts` depends on neither the design's code nor the plan's. `design-again` refuses a path that is neither light nor full.
6. `draw` (`scripts/lib/design-card.ts`) draws the design card: the answer, which design, which path, and whether approve is offered; the requirements' counts; each module, what it implements and owns, and what it hides as a judged line citing the designers' step, or the challenger's for a merged design; each rule of the module, by script, `rule <name>, in <module>: takes <values>; gives <values>`, each value by name with `from` or `into` its store, and what it decides as a judged line citing the same step; each interface and one line for each action with the conditions it serves, the rule it applies or that it applies none, what it reads and writes, and its count of examples, and for an action that serves none, its reason as a judged line citing the designer; coverage; how many checks the script made and every problem; the count of examples and what of them was checked against their actions' schemas, naming the input of each refusal, which is not checked, and, when any says a long text by rule, how many do; the practices the script's checks hold (P-35, P-36, P-38, P-42); when a second pass ran, what the first challenge answered not held and how many findings it gave, that the designer answered once, what the answer changed as `scripts/lib/design-compare.ts` lists it (modules, rules, interfaces and actions added or removed, what a module implements, owns and hides, what a rule takes, gives and decides, the rule an action applies and what it reads and writes, request and response schemas, an action's reason, its examples added, removed or changed, which actions serve each condition, and each practice's sentence, by name and never in the designer's words), and that the second challenge's answers decide; when none ran, that the designer was asked once and when a second answer is asked; the challenger's counts and each practice it answered not held as a judged line, followed by the designer's own sentence for that practice; the findings, each a judged line citing the challenger who gave them; on the full path where the two designs differed and why the challenger chose. Lines the answering designer or the second challenger wrote cite `design-again` and `challenge-again`. Approve is withheld while the check finds a problem or a practice held by design is answered not held; after a second pass the reason adds that the designer has answered the challenge once, which is the most a design run asks. A finding withholds nothing, as on the plan card.
7. `commit` (`scripts/commit-design.ts`) ends the run on `stop`. On approve it commits the design as it stands after `design-again`. It cuts `<job>-design` at `into`, writes `docs/designs/<job>/design.yaml` (the design as JSON, which is YAML, with each schema named by its path, each module's rules whole and each action's rule, reads and writes, and each long text as the designer said it) and `docs/designs/<job>/schemas/<interface>/<action>-request.json` and `-response.json`, commits them with `worktrees.commit`, merges with `worktrees.merge`, removes the worktree, keeping its branch, and drops the branch once the merge has landed. A merge that does not land leaves the branch and ends the run with `forge committed the work as <commit> on forge/<job>-design, but it did not land in <into>, so the branch stays and holds it:` and the merge's sentence. A branch of that name left by an earlier run is dropped before the cut and named under `dropped` with its commit. Its output names the commit, the merge commit, `into`, the design file and, as `interface`, every file written, in the form the workflow `rounds` takes.

Each worked example is held to its action's schemas by `context.schemas.checkAgainst`: the input and the answer of an example that answers, and the input of each earlier call against the request schema of the action it calls. A schema that names another file of its interface is checked with that file's schema in its `$defs`. A refusal's input is not checked, since the design does not say whether the schema or the action refuses it; its sentence must have words. A schema the kernel refuses (too large, a reference outside the interface, not a schema) is a problem of its own, naming the action and the side. An example's input, answer or earlier input may say a long text by rule, as `{"$text": [parts]}`, each part a text or `{"repeat": "<text>", "times": <count>}`, so a designer with only reading tools can give an example at a length limit; at least one part and at most 20, no part empty or holding half a surrogate pair, and at most 10,000 characters, a character being a Unicode code point, as a schema's `maxLength` counts. One pure function, `spelledOut` in `scripts/lib/long-texts.ts`, spells it out for every reader: the examples' check, the design check, the card's count and the leak check. A form past the bound, or one it cannot read, is a problem of the design naming the example and its side, and that value is not checked against the schema. What it does not hold: an answer's truth beyond its shape. The worktree `<job>-practices` is removed before any designer works; a leftover of that name from a run that ended early is removed and dropped before the cut. `forge/<job>-practices` is dropped as soon as its worktree is removed, and `forge/<job>-design` once its commit has landed, so a second design of one job starts clean and leaves no branch. The leak check counts every string of the interface files at the slice's base, a design's worked examples among them, as words both sides were given.

## Plan: from a committed design to a plan whose first wave can start

```
bay call --workflow forge:workflows/plan.yaml '{"design":"docs/designs/todo/design.yaml"}'
```

The steps: `start`, `plan-1`, `challenge-1`, `plan-2`, `challenge-2`, `draw`, the approval `card`, `commit`. No step repeats.

1. `start` (`scripts/plan-start.ts`) cuts `<job>-plan-reading` at the setting `into`, reads the design file and the practices held by a plan (rows whose holder is `plan`: P-33, P-34 and P-35 in the kit), removes the worktree, and checks the requirements file the design names with `requirements.check`. A refused file ends the run with every problem and its line, by the same code as the design's first step.
2. `plan-1` is the skill `plan` (the planner, tier balanced). The planner hands in a plan as data in `schemas/plan.json`. Its check, `scripts/plan-checked.ts`, sets `requirements` and `design` from the run and sends back every error `forge.waves` would name, at most three rounds.
3. `challenge-1` is the skill `challenge-plan` (the challenger, tier deep, another model than the planner, P-27). It answers each practice held by a plan, held, not-held or does-not-apply with a sentence, and gives findings. Its check, `scripts/plan-challenge-checked.ts`, is the design challenger's check of the answers by practice.
4. `plan-2` (`scripts/plan-again.ts`) asks the planner once again, with its first plan, each practice the first challenge answered not held and its findings, only when it answered a practice not held or gave a finding: the rule is `secondPassNeeded` in `scripts/lib/second-round.ts`, the design's. `challenge-2` (`scripts/challenge-again.ts`) asks the challenger to judge the answered plan once more, only when the planner was asked, with what the first answered not held and found and what the planner changed, by `scripts/lib/plan-changes.ts`; its answers decide the card. Each slice's title on the plan card is a judged line signed by the planner's step, cut at 60 characters.
5. `draw` (`scripts/lib/plan-card.ts`) draws the plan card: the answer first, how many slices in how many waves, the longest chain, and whether approve is offered; each wave with its slices, each with its module, its title cut to 60 characters, the conditions it meets and the rules of the design its actions apply, those of each action whose request file the slice names in `interface`, and the plan check names a slice that meets a condition while its interface names the request file of no action that serves it; the afters; coverage; whether every fixed file is made first; what the script checked and each problem; the practices the script's checks hold and the challenger's counts, each not held as a judged line; the findings left after the planner's answer as judged lines. Before the practices, when the planner answered: what the first challenge answered not held and how many findings it gave, that the planner answered once, what it changed, worked out by script, and that the second challenge's answers decide; otherwise that the planner was not asked again. Approve is withheld while the check finds an error or a practice held by a plan is answered not held; after the planner's answer the reason adds that the planner has answered the challenge once, which is the most a plan run asks. A finding withholds nothing.
6. `commit` (`scripts/commit-plan.ts`) ends the run on `stop`. On approve it cuts `<job>-plan` at `into`, writes `docs/plans/<number>-<job>.yaml` with the next free four-digit number in that folder, commits, merges, removes the worktree and drops its branch once the merge has landed, as the design's commit does. Its output names the commit, the merge commit, `into`, the plan file, and as `wave` the slice request of each slice of the first wave, in the form the workflow `rounds` takes, with the plan's commit as `base` and, in `rules`, the rules its actions apply, each with its module, what it decides, takes and gives, and each action of the slice that applies it with what it reads and writes. The workflow `wave` gives its slice requests the same `rules`, by `scripts/lib/slice-requests.ts`.

What it does not hold: `forge.waves` reads the design from the project's folder, the workflow from `into`. The design's version of the requirements is not compared with the file's version now.

## A wave: its slices side by side, the whole suite once

The workflow `wave` (`workflows/wave.yaml`) takes `{ "plan": "<committed plan>", "wave": <number> }` and builds that wave's slices side by side, as the owner chose in ADR 26: each slice proved by its own tests, bugs and scope, the whole suite once on the slices combined, and one merge card.

1. `wave` (`scripts/wave.ts`) names the wave `wave-<number>` and reads the plan at the head of `into` through `read-on-branch`, an action that cuts a worktree, reads and removes it, so a replay of the script reads the same text from the recorded answer. It works out the waves with the code `forge.waves` uses (`workOut`, the plan's requirements and design read as `forge.waves` reads them) and refuses, with every reason in one sentence each: a plan `forge.waves` finds an error in, a wave the plan does not have, a slice with no interface files (there is no `build-without-interface` in a wave), and two names that clash, one being the other with a dash and more, such as `A` and `A-2`, or a slice and the wave's name. `TD1` and `TD10` do not clash. A later wave is refused while a slice it comes after is not merged into `into`: forge knows a slice is merged when every test file its `fails-first` items name is at the head of `into`; a slice that names no such file cannot be shown merged, and the wave is refused with that sentence. Every slice is cut from that head. It looks for the branches an earlier run of the wave left that may hold work, each slice's as `look` does for the rounds and the combined branch `forge/wave-<number>`. The answer holds the start card, the slice requests in the form the workflow `rounds` takes, and `sideBySide`, the setting or 2 when it is left out.
2. `start` shows the start card: the plan and the wave, each slice in two lines (name and title; then its module, or its scope when the plan names no design, the conditions it meets and how many interface files), how many builders work side by side, which slices start first when there are more than that and that the others start as slices end, the most model calls a slice can take (27: `declare` and `plant` up to three answers each, `write-tests` and `review` three rounds of up to three, three builds) and the wave's, and that each slice's own proof leaves out the checks. Each branch an earlier run left is a line, as on the rounds' start card. Its choices are `build`, `build-over` and `stop`: `build-over` is offered when an earlier run left a branch, and `build` otherwise. On `build-over` each slice's `attempt` drops that slice's branches and `combine` the combined branch, each answering the commits. `begin` (`wave-begin`) changes nothing, so that the undo below runs, and ends the run on stop; from then on, a run that fails is undone by `forget-wave`, which forgets every slice's kept tests and findings.
3. `slices` is a `foreach` over the slice requests with `sideBySide: $steps.wave.output.sideBySide`, so at most that many builders work at once, and the next slice starts as soon as one ends. Each item is the rounds of one slice, the same actions as the workflow `rounds`: `slice`, `attempt`, `worktrees.cut`, `pin` at the wave's base, `declare`, rounds and reviews one to three, `bugs`, then `own-proof` (`slice-proof`, marked `calledOutputs: kept-packed`), which asks proof for the slice whole but for its `checks` items and filters the answer against the slice's kept tests without forgetting them, and `settle`, which hands the slice on with the reason its own proof did not pass, in the merge card's words (a must item failed or not known, the builder stopped, a leak, a must practice not held, an interface file changed), or none. Every slice is cut under its own name. `attempt` sets aside and removes the worktrees an earlier attempt of the slice left, and drops the slice's branches, answering each commit: on a first attempt there are none unless the owner chose `build-over` for them, and on a rerun of a failed item they are that item's own, whose rerun the owner chose. No fresh name is needed: two slices of a wave never share a name, since the wave refuses names that clash. When the rounds end, `review-n` drops the slice's earlier branches as in the workflow `rounds`.
4. A slice that stops, leaks or fails its own proof is not a run failure: its item ends with its verdicts. A script that fails or a skill whose answers are spent fails its item; the other items run to their end, and the kernel then asks the owner with a sentence naming every failed item, its key and its reason. `bay resume <run> --rerun` runs only the failed items again, each as a new attempt; `bay resume <run> --stop` fails the wave, and `forget-wave` forgets the kept tests. Both are the owner's answers: from a terminal, or with `--via chat --quote "<the owner's exact words>"` when `approvals.from` lists chat.
5. `combine` cuts `wave-<n>` at the base and merges each slice that passed its own proof onto it in plan order, through `worktrees@1`, each from a worktree `<wave>-<slice>` cut at the slice's last head, which is removed and its branch dropped after its merge. A merge that does not apply stops it: the card names that slice, those merged before it and git's sentence, and merge is withheld.
6. `prove` (`prove-checks`, kept packed, a script limit of 3,600 seconds) asks proof once for the toolchain's checks and the whole test run on the combined head, filtered against the kept tests of the slices in it. When the checks item fails, `alone` proves each slice in the combined head alone with its own `checks` items at its own head, at most `sideBySide` at once, so the card can name the slice whose work breaks the suite, or say that each passes alone and only their combination fails.
7. `draw` (`draw-wave`) draws the merge card by `scripts/lib/wave-card.ts`. It leads with the answer: merge offered for N of M slices, and the slices left out; or not, and why. Then, for each slice, its title; whether it is in the combined head or left out, with the reason, where its work and tests are and where the builder's work alone is, and that its branches stay; its items and verdicts as the slice's merge card prints them (`item-lines.ts`); the practices the reviewer answered, and each it answered not held as a judged line, must marked; its interface files by hash; the bugs the planter wrote and each that survived; each leak; the rounds and why they ended, the round the reviewer judged in, and the reviewer's and the builder's judgement as judged lines, as the slice's merge card shows them. Each judged line cites its step with the slice's item in `slices` (`quotes` lists `review-1` to `review-3` and `round-1` to `round-3`), so the kernel names the skill and the item under it. Then the combined head, its checks with proof's reason when they did not pass, each slice proved alone and the breaker. Merge is offered only when at least one slice passed its own proof, each such slice merged cleanly, and the wave's checks passed.
8. `carry-out` (`carry-out-wave`) forgets every slice's kept tests, on merge and on keep. On merge it cuts `<wave>-merge` at the combined head and merges it into `into` as the rounds' carry-out merges a slice (the checked-out branch is fast-forwarded only when clean), then removes that worktree, and drops the merge branch, the combined branch and the two branches of each slice in the combined head; a slice left out keeps its two. On keep every slice keeps its two and the combined branch stays when the card names it; with no combined head it is dropped. The answer's `kept` lists exactly the branches that stay. No worktree stays.

What it does not hold: a builder's agent may write anywhere under `.forge/worktrees/`, another slice's worktree included: a write outside its slice is caught afterwards by proof's `scope`, not stopped. A submit that arrives while another call advances the run is recorded and answered as accepted, and the run takes it once, when that call ends or at the next resume; a submit the kernel refuses keeps its token. Proof names its throwaway copies by the clock's milliseconds, so two proofs that start in the same millisecond can ask for one name.

## The plan's form

`schemas/plan.json`: a title, and a list of slices, each a title and a slice, with the optional fields `docs/plans/README.md` gives. The slice is `proof@1`'s slice, held by reference to `proof@1/prove-request.json#/$defs/slice`, so the two cannot drift. That is why forge requires `proof@1`, and why the kit's config binds `proof`.

Whether two scopes share a path is one pure function, `scripts/lib/scopes.ts`. It matches paths with the toolbox's `pathMatch`, the matching `proof@1`'s kind `in-scope` uses, and it confirms every example path with it. A pattern `pathMatch` refuses is never answered "share no path".

## Settings

`into`: the branch a merge goes into. `practices`: the practices files a builder reads, relative to the project.

`mustPractices`: the ids of the practices the workflow `rounds` treats as must, such as `P-12`. While the reviewer's last answer says one of them is not held, the merge card withholds merge and names it; keep stays. Left out, none: a practice not held is shown on the card and withholds nothing. The kit sets P-12, P-52, TS-17, TS-21 and TS-25. The workflows `design` and `plan` do not read it: there every practice held by design or by a plan withholds approve when the challenger answers it not held.

`sideBySide`: how many builders the workflow `wave` runs at the same time, from 2 to 8; left out, 2. A wave with more slices starts the next one as soon as one ends, and proves its slices alone the same way.

`featureMap`: the project's map of features, such as `framework/features.yaml`. Forge reads each feature's private files from it for the warning on a whole feature. Left out, no scope is compared with a feature. The kit sets it.
