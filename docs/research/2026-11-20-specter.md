# Specter, read for forge's design, planning and waves

Read on 19 November 2026 from a shallow clone of `devagrawal09/specter` at commit `84ffff5` (12 November 2026), in `/tmp/specter-study/repo`. Nothing in it was run. Paths below are relative to that clone unless they start with an agentbay folder.

## Licence and how I read it

The licence is MIT (`LICENSE`, "Copyright (c) 2026 Specter contributors"). Every `package.json` that has a licence field says MIT, including `packages/core/package.json`, `packages/spec/package.json` and `apps/agent-runtime/package.json`. MIT is permissive, not copyleft. This note takes ideas only. It copies no code, schema, prompt or document text. Names of concepts appear as a few words at most.

## Answer in brief

1. Specter is an event-sourced TypeScript runtime in which each command, query or reaction is a slice with a data file of exact given/when/then examples beside its code.
2. Its verification is real but narrow: a structural check at app start, a runner that replays each example against the real handler, and a runtime guard on which event types a command may emit. The README says itself that this proves only the declared examples.
3. The tagline "state machine explicit and verified" has no artefact behind it. There is no state or transition format anywhere in the code; the state machine is implicit in event histories and handler guards.
4. Its "OpenSpec workflow" is one temporary change file per change, deleted before merge. It has no design step, no plan of slices, no waves and no independent test writer; the same agent writes examples and code.
5. Forge already holds more of the process (hidden tests, planted bugs, leak check, cards, scope). Specter holds more at the interface: examples that are data and are checked against schemas, coverage rules in both directions, and an impact report for a changed shared contract.
6. Worth taking, for DS1 and PL1 mostly: worked examples on each interface action, checked by script; two-way coverage between conditions and actions; an impact report for an interface file; hashes of interface files bound to the verdict; a wave that reports every slice's failure at once.
7. Not worth taking: the runtime, Effect, event sourcing as a style for modes, the temporary deleted plan, and first-wins idempotency.

## 1. What Specter is

**What a developer writes.** For each slice, two files (`docs/architecture/vertical-slice-architecture.md`, `docs/architecture/file-structure.md`):

- `spec.ts`: the slice's kind, name, a description, and at least one scenario. A command scenario has a list of prior events, an input, and either the exact events expected in order or an empty list with an exact rejection message (`docs/specifications/writing-specifications.md`, "Command Scenarios"). A query scenario has prior events, an input and the exact output. A reaction scenario has prior events and zero or one expected effect.
- `impl.ts`: a staged builder that adds an input or output schema, a private store, one apply handler per event type it projects, and the final handler; a reaction also adds a plugin that carries out its effect (`CONTEXT.md`, "Slice Implementation").

Beside these the developer writes event definitions: a kebab-case type and a payload schema that must not transform the payload (`CONTEXT.md`, "Event Definition"). A feature folder holds an event catalog and a registry (`apps/reference/src/features/todos/`).

`spec.ts` is exported to `spec.json`, a strict, versioned JSON document (`specification/schemas/slice.schema.json`, `specification/README.md`). The implementation reads only the JSON. A canonical SHA-256 digest is defined over it (`specification/README.md`). A Go runtime reads the same JSON (`runtimes/go/README.md`), and a local editor edits it with a stale-revision check on save (`packages/spec-editor/README.md`).

**What the framework runs.** One event log per app; per-slice private state with its own cursor; commands that catch up, decide and append in one transaction against a version; idempotency keys; latest-value query subscriptions; and reactions that run after commit, one delivery per relevant commit with a stable delivery id (`docs/architecture/runtime.md`, "Reactions"; `CONTEXT.md`, "Reaction Run", "Reaction Delivery"). An optional outbox package runs slow plugins outside the transaction with leases, retries and dead letters (`docs/api-reference/reaction-outbox.md`).

**What it verifies, and how.** Three layers (`docs/specifications/conformance.md`):

- At app construction, without running any handler: event types unique and kebab-case; every registered event used in at least one scenario; slice names and descriptions well-formed; scenario descriptions unique; each scenario event known and valid against its schema, which must not change it; each command or query input valid against its input schema; and the set of event types in a slice's prior events equal to its apply handlers, both ways. All problems are gathered into one error.
- In the scenario runner (`docs/specifications/slice-tests.md`, `packages/core/src/testing/scenarios.ts`): for each scenario, replay the prior events into a fresh store with fixed ids and times, call the real handler, and compare by exact structural equality. A rejection matches on the exact message string. A reaction's plugin is not run; only the returned effect is compared.
- At runtime: a command that emits nothing is rejected; a command may emit only event types that appear in one of its accepted scenarios; inputs and outputs are decoded at the edge; the log's order is checked.

**Its own statement of the limits.** The README says that "verified" means checked against the declared scenarios and constraints, that construction checks structure and not the scenarios, that no check proves every history or input, and that reaction tests do not run the plugin (`README.md`, "Check the Implementation"). The roadmap adds that a well-formed scenario is not proof that an implementation passes it, and that generated tests cannot find missing business rules (`roadmap.md`, "Visual Slice Scenario Editor", "Tests Generated From Schemas", "What Remains Specter's Responsibility"). One more limit the repository does not state plainly: in today's flow the agent that writes the scenarios also writes the code (`.agents/skills/specter/SKILL.md`, "Feature Workflow"), so the scenarios check that code and examples agree, not that the examples are the right ones. The roadmap's planned pipeline moves scenario authoring to people in a shared workspace and the code to an agent (`roadmap.md`, "Specification-To-Preview Pipeline"). It is not built.

**The state machine.** A search of `packages/spec` and `packages/core/src` finds no state, transition or machine format. The only use of "state machine" outside the tagline is a domain description in `docs/evaluations/2026-07-16-multi-app-specter-evaluation.md`. The machine exists only as scenario histories plus handler guards. Nothing checks that every state and transition is covered.

## 2. The spec format and the OpenSpec workflow

**Artefacts between an idea and code**, as the repository has them:

| Artefact | Written by | Checked by script | Checked by a model |
|---|---|---|---|
| OpenSpec change file `openspec/changes/<name>/spec.md`: goal, scope with non-goals, required behaviour, tasks, validation (`openspec/schemas/ongoing-change/templates/spec.md`) | the coding agent through a propose skill (`.codex/skills/openspec-propose/SKILL.md`) | shape only: one file per change, no archive, no permanent specs, the shared schema used (`scripts/validate-openspec.mjs`) | none in the repo; a person reviews the pull request |
| Event definitions | the agent | construction conformance | none |
| `spec.ts` and its `spec.json` | the agent, or a person in the editor | strict schema, conformance, digest (`packages/spec/src/validation.ts`) | none |
| `impl.ts` | the agent | type check, import boundaries (`scripts/check-slice-imports.mjs`), scenario runner | none |

The change file is temporary. It is deleted before merge, after lasting facts move to READMEs (`docs/guides/openspec.md`, "One-file lifecycle"). Each package and app has its own OpenSpec root, and a change spanning several gets one change file each (`AGENTS.md`, "OpenSpec Scope"). The change file must not copy scenarios; it points at them (`docs/guides/openspec.md`, "Keep OpenSpec and Specter distinct").

**Against agentbay.**

- Agentbay's requirements file (`docs/designs/pm-mode/design.md`, section 2) is closer to what a person sees: outcomes, conditions in given/when/then as sentences with literal values, refusals with what is seen after, versions and sign-off. Its check holds wording rules (section 4). It is not executable. Specter's scenarios are executable but sit at the level of one operation's input and output. They correspond to forge's interface schemas plus the test writer's cases, not to requirements.
- Specter has no design step. Nothing names modules, what each hides, or who owns what is stored, before code. The only design rules are architectural constants: slices own their state, share only events, and do not import each other (`docs/architecture/vertical-slice-architecture.md`, "Ownership and dependencies"). Forge's DS1 (`docs/designs/forge-whole/A.md`, section 2; ADR 28 point 2) is a step Specter lacks.
- Specter has no plan of slices. The change file has task checkboxes, not slices with scopes, afters or waves. Forge's plan (`components/base/forge/README.md`, "The plan's form") and `forge.waves` have no counterpart.
- The temporary, deleted change file contradicts agentbay's rule that a merged slice stays in its plan (`CONTEXT.md`, "Plan"). The rule "do not copy scenarios into the change file" matches P-12 (one place for a rule).

## 3. Vertical slices and their independence

**Specter's slice** is a runtime unit: exactly one command, one query or one reaction, with its own spec, implementation and private state (`CONTEXT.md`, "Slice", "Slice State"). Independence is held by:

- private state: no slice reads another's state; a query's state never drives a command's decision (`docs/architecture/vertical-slice-architecture.md`, "Invariants and pitfalls");
- events as the only shared contract, registered once in the app;
- a script that refuses an import of a sibling slice inside the same feature, a `spec.ts` that imports anything but the spec package or files whose names suggest implementation, and an `impl.ts` that imports `spec.ts` instead of `spec.json` (`scripts/check-slice-imports.mjs`, `checkFile` and `checkSpecificationImport`);
- an impact report that lists, for one event type, every producer, every scenario that uses it and every consumer (`packages/core/src/testing/event-propagation.ts`, `docs/specifications/writing-specifications.md`, "Evolve an Event safely").

The README says independent slices can be built in parallel (`README.md`, "Give Agents a Smaller Problem"). The repository has no mechanism for that: no work unit, no scope, no order, no waves.

**Against forge.** A forge slice is a unit of work: a write scope, afters with reasons, interface files, and a definition of done (`CONTEXT.md`, "Slice"). Waves come from disjoint scopes and no order (`CONTEXT.md`, "Wave"). Specter's slice is closer to a forge module than to a forge slice. The useful link: in Specter one operation is one folder, so a work unit's scope is a folder by construction. That is ADR 25 point 7 (module boundaries become scopes) carried to the finest grain.

**Against the practices** (`framework/practices.md`):

- P-36 (named for what it does): slice folders are named for the use case. Matches.
- P-37 (small surface over much work): one operation per slice is a small surface, but many slices repeat projections of the same events. The project's own evaluation names that repetition as a cost (`docs/evaluations/2026-07-16-multi-app-specter-evaluation.md`, "Private projections and exact scenarios create repetition"). Specter accepts duplication over shared state on purpose (`AGENTS.md`, "Code Style"). That is in tension with P-12.
- P-38 and P-42 (a module owns its data): private slice state is this rule, held by structure and partly by the import script.
- P-39 (one way): `spec.ts` cannot import implementation, held by script. Matches.
- P-40 (what changes together lives together): spec, code and private tables sit in one folder. Matches.
- P-41 (tests with the module): the scenarios sit in the slice; the runner is the test. Matches.
- P-52 (rules are pure): command handlers must be deterministic; ids, times and randomness enter as input (`CONTEXT.md`, "Command Slice"; `.agents/skills/specter/SKILL.md`, "Determinism And Transport"). Store access is through read-only state in handlers and write-capable state only in apply handlers. A close match, and held partly by structure.

## 4. Scenarios as tests

Yes: they are given/when/then over events, with exact values. Given is a list of prior events, when is one input, then is the exact list of events, the exact output, or an exact rejection message (`docs/specifications/writing-specifications.md`, "Scenario shapes"). Invalid input is never a scenario; malformed input is a schema test elsewhere (`docs/specifications/slice-tests.md`, "Schema validation versus domain behavior").

What forge could take:

- **Runnable examples belong at the interface, not in the requirements.** Agentbay's requirements are for a person and name no kind of proof (`docs/designs/pm-mode/design.md`, "No kind of proof in the file"). That should stay. A design's interface action, though, could carry worked examples: prior calls, one input, the exact answer or the refusal's sentence. A script can then check each example against the action's request and response schemas, as Specter checks each input against its schema at construction. The test writer receives them as cases it must include; it still adds its own hidden cases. Design A once had an optional `example` with a command and its printed text (`docs/designs/forge-whole/A.md`, section 1, "Form"); the PM design dropped it. The design is the right place for it.
- **Given as earlier calls, not as a described state.** Specter's given is a history, so no one has to describe a state in prose. For forge modes the analogue is a list of earlier action calls. It is exact and a test writer can replay it.
- **Two-way coverage.** Specter refuses an event no scenario uses and an apply handler no scenario needs. Forge can refuse an interface action that no condition needs and a condition that names no action.
- **A state machine per module.** Specter does not have one, despite its tagline. For a module that stores a thing with a status, a design could list the states and, for each action, the states it moves between. A script could then check that each listed move is met by a `works` condition and each refused move by a `refused` condition. It fits only stateful modules and should be optional.

## 5. Process model

Specter's only process is the reaction: after a commit, each reaction slice catches up, and for each relevant commit it may produce one effect, carried out by a plugin or dispatched as a command with the delivery id as its idempotency key (`docs/architecture/runtime.md`, "Reactions"; `docs/architecture/plugins.md`). A failure rolls back that reaction's state and cursor and retries the same commit with the same delivery id. Failures of independent reactions are gathered after the pass, and the command's own commit stands (`CONTEXT.md`, "Reaction Run Failure", "Command Execution"). The outbox adds leases, heartbeats, retries with backoff and dead letters, outside the core and only when asked for (`docs/api-reference/reaction-outbox.md`). There is no timer step, no human approval, no workflow file and no long-running saga beyond a reaction's own state.

Agentbay's workflow (`schemas/workflow.schema.json`) is a list of steps: action, approval with choices and rules, wait for a duration, and foreach. Runs are durable and resume with finished calls replayed (`docs/designs/forge-whole/A.md`, section 4, "Why rounds need no kernel change"). There are no parallel steps and no loops; forge unrolls its rounds (`components/base/forge/workflows/rounds.yaml`).

The two models solve different problems. Specter reacts to facts with no person in the loop; agentbay drives a known sequence with the owner at fixed points. Three things transfer:

- A stable identity per delivery, used as the idempotency key downstream. Agentbay has the run and step ids; a script that calls an outside system could pass them as its key.
- One failure does not undo another's success, and all failures are reported after the pass. This is the shape WV1 needs (section 6, idea 5).
- Retry machinery is an opt-in at the edge, not part of the core (`AGENTS.md`, "Architecture Simplicity"). That supports agentbay's choice to keep the workflow form small.

## 6. What each lacks, and what not to take

**What Specter does that agentbay lacks:**

- examples that are data, checked against the action's schemas before any test runs;
- coverage both ways between examples and the parts they exercise;
- an impact report for a change to a shared contract;
- a canonical digest of the contract, and a roadmap item to bind each verification to the digests of the spec and of the artefact (`roadmap.md`, "Verification Attestations");
- a structural rule that the contract cannot import the implementation, held by script.

**What agentbay does that Specter lacks:**

- the test writer and the builder are different agents, and the builder never sees the tests (ADR 24, ADR 27);
- planted bugs written by a party that never saw the tests, and a leak check (`components/base/forge/README.md`, "Rounds");
- a reviewer at a stronger tier that answers by practice (ADR 28);
- write scope and declaration, proved by script;
- a design step, a plan, waves, and the owner's approval on cards whose lines say who judged them;
- requirements a person signs off, with versions.

**What would be a mistake to take:** see "Not worth taking" below.

## Ideas worth taking

**1. Worked examples on each interface action.**
- Idea: the design gives each action in an interface at least one example of earlier calls, one input, and the exact answer or refusal sentence. A script checks every example against the action's request and response schemas.
- Lands in: design DS1; the test writer's input in the rounds.
- Smallest form: an optional `examples` list per action in `design.yaml`; `draw-design` validates each against the schema files and prints a computed count on the design card.
- Cost or risk: more designer work. The builder sees the examples, so it can fit to them; the hidden cases still judge it. The leak check must count the examples as words both sides were given, or it will flag them.

**2. Coverage both ways between conditions and actions.**
- Idea: refuse a design in which an interface action serves no condition, as well as a condition that names no action.
- Lands in: design DS1 (the design's `meets`); planning PL1 repeats it for slices.
- Smallest form: one more problem in the design check, beside the three ADR 28 point 2 lists.
- Cost or risk: low. Some actions exist for operators, not for a condition; they need a stated reason, as `oneAfterAnotherBecause` gives one for a chain.

**3. An impact report for an interface file.**
- Idea: for one interface file, list the slices that build against it, the conditions they meet and the tests named for them.
- Lands in: planning PL1, and the change flow when requirements change after building started (`docs/designs/pm-mode/design.md`, section 6).
- Smallest form: an optional input to `forge.waves` naming one path; its output gains that list. It is a pure function over the plan.
- Cost or risk: low. It is only as good as the slices' declared interface files, which PL1 makes required.

**4. The interface's hash bound to the verdict.**
- Idea: record the hash of each interface file and of the requirements version when a slice is cut, and again when proof judges it. A difference withholds merge and says which file changed.
- Lands in: proof and the cards (start card, merge card).
- Smallest form: the step `slice` records the hashes; `draw` compares them with the head's and adds a computed line. A withheld merge with its reason.
- Cost or risk: small. A legitimate interface change during the rounds then needs the owner to start again, which is the intent of fixing interfaces first.

**5. A wave reports every slice's failure, and one slice's failure undoes no other's verdict.**
- Idea: in a wave, each slice's proof stands for that slice. The whole-suite run on the combined result is a separate line. When it fails, the card names every slice whose solo proof then fails, not only the first.
- Lands in: waves WV1, and its merge card.
- Smallest form: WV1's script runs each slice's proof, gathers all answers, then runs the whole suite once; the card lists all failures with the slice each belongs to.
- Cost or risk: more proof time when the whole suite fails. WV1's definition of done already asks for proving each slice alone in that case.

**6. A state machine per stateful module, optional.**
- Idea: for a module that stores a thing with a status, the design lists its states and which action moves it from which state to which. A script checks that each move is met by a `works` condition and each refused move by a `refused` condition.
- Lands in: design DS1; the test writer reads it.
- Smallest form: an optional `states` block per stored thing in `design.yaml`, checked against the conditions' ids that name it.
- Cost or risk: it fits only stateful modules, so it must stay optional. Linking a condition to a move needs a field on the condition or in `meets`; that is one more thing to keep in step.

**7. The contract may not import the implementation, held by script.**
- Idea: the files a design fixes (schemas, interface files, examples) may not refer to the code that implements them. A slice's fixed files are data only.
- Lands in: planning PL1 (fixed files), and proof's `checks` through the toolchain.
- Smallest form: a check in the design step that each interface file is a schema or YAML with no reference into a module's scripts.
- Cost or risk: low. It mostly holds already by form; the check makes it explicit.

## Not worth taking

- **Specter or Effect as a dependency.** The core is Effect-native with a Promise facade (`README.md`, "Build on Durable Facts"); plugins must stay inside Effect to keep transaction context (`.agents/skills/specter/SKILL.md`). Agentbay's kernel never depends on a framework under it (`framework/practices.md`, "Considered and not adopted").
- **Event sourcing as the style of modes.** Modes are actions with schemas over a database partition. An event log per mode, private projections and replay would add a second source of truth to what the kernel's runs already record.
- **Exact rejection message as the only check.** It makes a refusal's wording part of the contract, which is brittle. Agentbay's refused conditions ask for a literal that the sentence contains, plus what is seen after (`docs/designs/pm-mode/design.md`, section 4). That is better.
- **A temporary plan deleted before merge.** It throws away the record of why slices were cut. Agentbay keeps plans and ADRs by rule.
- **The OpenSpec CLI.** Its shape checks are a file count. Forge's own checks of a plan already do more.
- **First-wins idempotency across different payloads.** A repeat with a different payload returns the first result as a duplicate unless the caller opts out (`CONTEXT.md`, "Idempotency Key"). It hides a caller's mistake. Agentbay's replay by step identity is stricter.
- **The same agent writing examples and code.** That is Specter's present flow. It conflicts with ADR 24.
- **A spec in two source forms, `spec.ts` exported to `spec.json`.** Two forms need a sync rule; the roadmap admits it (`roadmap.md`, "Specification-To-Preview Pipeline"). Agentbay writes YAML and JSON directly.
- **Outbox leases and dead letters in the kernel.** Agentbay's workflows have no parallel steps and no background workers. The machinery has nothing to serve yet.
- **The word "verified".** The tagline promises more than the checks hold. A card that said "verified" on the same grounds would break the rule that a card says who judged each line.
