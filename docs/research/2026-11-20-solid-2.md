# Solid 2.0: what shipped and whether agentbay should use it

Researched 19 November 2026 (US Eastern). Sources are named inline. npm data was read straight from registry.npmjs.org. Size figures marked "my measure" come from bundling run in /tmp/solid-study.

## Answer in brief

- Solid 2.0.0 stable went out on npm on 17 Nov 2026 at 05:19 UTC. `latest` is now 2.0.3 (19 Nov). `next` still points at 2.0.0-rc.23. The 1.x line moves to the `v1-latest` tag (1.9.20).
- The @solid_js post was almost certainly the stable announcement. Decoding its status ID puts it at 17 Nov 2026, 19:05 UTC, about 14 hours after 2.0.0 hit npm. The blog post "Solid 2.0 - The Long Hold" is dated 16 Nov.
- 2.0 is a rewrite of the reactive core. Async is built into signals and memos. `Suspense` becomes `Loading`. Effects are split into a compute half and an apply half. Writes batch on a microtask. Server functions move into core. The `createResource`, `batch`, `on`, `produce` and `startTransition` APIs are gone.
- Migration is real work. Ecosystem support is uneven: TanStack is at RC, Kobalte is at alpha, and the testing library is at RC. SolidStart is retired and stays on 1.x.
- Nobody has published independent runtime benchmarks for 2.0 yet. On my measure the minimum runtime is about 3.5 times larger than 1.x.
- For the floor-plan sketch: no. A script that writes plain SVG inside one HTML file is simpler and fits the no-build rule.
- For the cloud dashboard: maybe later. A no-build path exists (`@solidjs/html` tagged templates, which I ran). Reconsider in 3 to 6 months, once UI kits ship 2.0 and agents have been shown to write correct 2.0 code.

## 2. What changes from 1.x

Main sources: the migration guide, MIGRATION.md in the repo (https://github.com/solidjs/solid/blob/main/documentation/solid-2.0/MIGRATION.md), the RFCs, and the CHEATSHEET.md that ships inside the npm package.

**Async in the graph.** A memo can return a Promise or an async iterator. Code downstream sees the resolved value, and the graph suspends and resumes itself. This replaces `createResource`.

```tsx
const user = createMemo(async () => fetchUser(id()));
<Loading fallback={<p>Loading</p>}>
  <p>{user().name}</p>
</Loading>
```

**Loading and pending.** `Suspense` is renamed `Loading`, and it applies to the first load only. `isPending(() => expr)` reports that a newer value is on its way while the stale value stays on screen. `latest(fn)` lets you read the in-flight value. `SuspenseList` becomes `Reveal`. Transitions are built in, so `startTransition` and `useTransition` are removed.

**Mutations.** `action(...)` plus `createOptimistic` and `createOptimisticStore` show the expected value at once. They roll back or reconcile when the server answers. `refresh()` replaces refetch.

**Effects split.** `createEffect(compute, apply)` is the only form. The compute half tracks dependencies. The apply half runs the side effect without tracking and returns its own cleanup. Because of this, the `on` helper is no longer needed.

```ts
createEffect(() => title(), (value) => { document.title = value; });
```

`onMount` becomes `onSettled`. `createComputed` is removed.

**Batching and scheduling.** Every write batches on a microtask. A read straight after a set still returns the old value. `flush()` applies pending writes immediately, mostly for tests. `batch` is removed.

```ts
setCount(1);
count();
flush();
count();
```

The first `count()` returns 0. After `flush()`, `count()` returns 1.

**Strictness.** In dev mode, Solid warns when a component reads a reactive value at its top level, which includes destructured props. It also warns when code writes signals inside a reactive scope.

**Stores and projections.**
- Store setters are now draft-first: you mutate a draft, as `produce` did before, so `produce` is removed. Path-argument setters become draft writes.
- `unwrap` becomes `snapshot`. `mergeProps` and `splitProps` become `merge` and `omit`.
- `createStore(fn)` and `createProjection` give derived, writable or keyed stores and replace `createSelector`.
- `createSignal(fn)` gives a writable derived signal.
- `createMutable` moves out of core into `@solidjs/signals`.

**Error boundaries.** `ErrorBoundary` becomes `Errored`. Boundaries heal on their own once their content works again, so `resetErrorBoundaries` is gone. `onError` and `catchError` are removed. Effects take an `error` option instead.

**Lists and control flow.**
- `Index` is removed. Use `<For keyed={false}>` instead, which passes item accessors and a numeric index.
- `Repeat` renders by count.
- `<Dynamic>` gives way to a `dynamic(source)` factory. `<Dynamic>` still works but is deprecated.

**DOM.**
- Attributes now follow HTML: standard boolean attributes, and `class` accepts objects and arrays. `classList`, `attr:`, `bool:`, `on:`, `oncapture:`, `use:` directives and `/*@once*/` are removed.
- Directives become ref factories, and an array of refs composes several.
- Ref callbacks are no longer owned, so calling `onCleanup` inside one no longer works.
- A context object is now the provider itself: `<Ctx value={...}>`.

**Packages and imports.**
- `solid-js/web` becomes `@solidjs/web`.
- `solid-js/store` merges into `solid-js`.
- `solid-js/html` becomes `@solidjs/html`, and `solid-js/h` becomes `@solidjs/h`.
- The reactive core lives in `@solidjs/signals`.

**TypeScript.** Renderers now own the JSX types. Set `"jsxImportSource": "@solidjs/web"`, and import `JSX` and `ComponentProps` from `@solidjs/web`. `solid-js` exports a renderer-neutral `Element` type, and `solid-js/jsx-runtime` is removed. Source: RFC 09, https://github.com/solidjs/solid/blob/main/documentation/solid-2.0/09-typescript-jsx.md

**SSR and streaming.** Source: RFC 12.
- Client entry points are `render` and `hydrate`. Server entry points are `renderToString` and `renderToStream`.
- `renderToStream` flushes the shell first, then streams each async boundary as it resolves. Awaiting the stream gives the full HTML, and `renderToStringAsync` is removed.
- A per-primitive `ssrSource` option ("server", "hybrid" or "client") and a `deferStream` option control how values hydrate.
- `clientOnly` moves into `@solidjs/web` from SolidStart.
- The RC post describes a Start mode in the Vite plugin, `solid({ start: true, ssr: true })`. It comes with a web-standard `handleRequest(request)`, middleware, typed env vars, and a build check that stops server secrets from leaking to the client.

**Server functions.** `"use server"` is now part of core through `@solidjs/web/server-functions`. It provides typed RPC, streaming, SSE-based `live()` and progressive enhancement. Source: RC and Long Hold posts.

**Compiler.**
- The default compiler is now Rust-based and built on Oxc, inside `@solidjs/vite-plugin` (3.0.1, which needs Vite 8 or 9). The Babel preset still exists.
- The RC post reports compile speedups of 23x to 355x over Babel. These figures are compile time, not runtime.

**Agent tooling.**
- Dev builds report reactive mistakes with a stable code, the source location and a suggested fix. One example is `STRICT_READ_UNTRACKED`.
- `solid-js` ships `diagnostics.json` (75 entries), a CHEATSHEET.md that opens with a warning aimed at AI code generators, and SKILL.md files under `skills/`. I checked these in the installed package.
- The Long Hold post also mentions experimental ReactiveScript and TSRX syntaxes, Chrome Performance Tracks and a Sentry plugin.

## 3. Migration from 1.x

**What breaks.** Almost every app will need changes in these areas:
- imports and the tsconfig JSX setting
- every `createResource`, `Suspense` and `ErrorBoundary`
- every single-function `createEffect` and `on`
- store path setters and `produce`
- `Index`, `classList` and `use:` directives
- `Context.Provider`
- `onMount`
- code that reads a signal straight after setting it, because of the microtask batching

**Official help.**
- The maintained migration guide: https://github.com/solidjs/solid/blob/main/documentation/solid-2.0/MIGRATION.md . The docs site has a version at docs.solidjs.com/migration/from-solid-1, which I could not fetch. The copy I read was a Netlify deploy preview of the docs.
- The migration assistant is `npx solid-migration-assistant` (npm 0.2.1, 13 Aug). It flags 1.x patterns. The RC post does not call it a full codemod.
- The docs keep `storePath()` to make store migration gradual.

**Ecosystem, from npm today:**
- `@solidjs/router` 2.0.1 is `latest` and needs solid-js ^2.0.0. It was published 20 Nov 03:04 UTC, which is late on 19 Nov in US Eastern time.
- `@solidjs/meta` 2.0.0 is `latest` and supports 2.0.
- `@solidjs/start` `latest` is 2.2.3 and still needs solid-js ^1.9. The Long Hold post says SolidStart is retired. The RC post says it gets maintenance releases, and that Start mode in the Vite plugin plus a router-neutral filesystem-routing package replace it. A SolidStart app has two choices: stay on 1.x or move off SolidStart. Coverage by byteiota (https://byteiota.com/solidjs-2-async-signals-smaller-api/) counts this as the hardest part of the move.
- TanStack is at RC: `@tanstack/solid-router` and `@tanstack/solid-start` 2.0.0-rc.11 (19 Nov) and `@tanstack/solid-query` 6.0.0-rc.6 (18 Nov) all support 2.0. Their `latest` tags still target 1.x. The Long Hold post says TanStack Query and Router work as well as first-party tools.
- Kobalte: `latest` is 0.13.14 and needs 1.9. The 2.0 build is 2.0.0-alpha.4 (20 Oct), pinned to rc.16.
- `@ark-ui/solid` 5.40.0 and `@corvu/*` declare peer solid-js >=1.6 or ^1.8. That says nothing either way about 2.0 support.
- `@solidjs/testing-library` 1.0.0-rc.2 (21 Oct) supports 2.0. `latest` is still 0.8.10 for 1.x.
- `vite-plugin-solid` `latest` is still for 1.x. 2.0 uses `@solidjs/vite-plugin` 3.0.1.

## 4. Performance and size

**Team claims.**
- The only numbers are the compile-time figures in the RC post: 440 ms to 19 ms on 88 fixture files, and 25 s to 70 ms on a 1 MB module. The measurement setup is described only at that level.
- The Long Hold post gives no runtime or size benchmarks. Its case is about less code and automatic handling of race conditions.

**Independent.**
- I found no published js-framework-benchmark result for 2.0. The benchmark's Solid entry on GitHub master still depends on solid-js ^1.9.3: https://raw.githubusercontent.com/krausest/js-framework-benchmark/master/frameworks/keyed/solid/package.json
- byteiota says the runtime grew from about 4.8 KB to 20.3 KB brotli. It names no method or source, so treat that as unverified.
- Several 2026 comparison blogs turn up in search. They mostly measure 1.x and are not primary sources.

**My measure.** esbuild with minify, production browser build, gzip -9, a counter button:

| Build | Solid 1.9.20 | Solid 2.0.3 |
|---|---|---|
| Signals and a manual effect, no JSX | 3.0 KB | 10.5 KB |
| `html` tagged template plus `render` | 11.6 KB | 21.7 KB |

So the minimum 2.0 runtime is about 3.5 times the size of 1.x. This fits the claim that the async scheduler is what costs the extra bytes. It is still small next to React (react plus react-dom is roughly 45 to 60 KB gzip; that is general knowledge and I did not measure it here). I did not measure runtime speed.

## 5. Comparison for a new small app

Current versions from npm: React 19.3.1, Svelte 5.58.0, Vue 3.5.45 (3.6 is at rc.15), Qwik 1.20.4 (Qwik 2 is at 2.0.0-rc.5 under `@qwik.dev/core`).

- **Model.**
  - Solid 2: fine-grained signals, and components run once. Async is now built into the graph, which neither React nor Svelte does as fully.
  - React 19: re-renders components, plus hooks, with the compiler as an option.
  - Svelte 5: runes, compiled.
  - Vue 3.5: proxy-based refs and a virtual DOM, with Vapor mode coming in 3.6.
  - Qwik: resumability, aimed at large content sites.
- **Learning curve.** Solid looks like React but behaves differently. Destructured props lose reactivity. You read a signal by calling it. Writes now land late, on the microtask. Svelte and Vue are the easiest for a newcomer. React is the most familiar.
- **Ecosystem.** React is far ahead. Vue and Svelte have mature UI kits. Solid 2's ecosystem is days old, and its main UI kit is at alpha. Qwik's is small.
- **SSR.** All five have streaming SSR. Next or React Router, Nuxt, SvelteKit and Qwik City are stable meta-frameworks. Solid 2 has a Vite plugin Start mode and TanStack Start at RC, and SolidStart stays on 1.x.
- **Stability.** React, Svelte 5 and Vue 3.5 are stable lines. Solid 2.0 is days old and at 2.0.3. Qwik 2 is still RC.
- **Hiring.** React leads by a wide margin. Vue comes second. Svelte and Solid are niche.
- **AI coding agents.** Models have seen far more React than anything else, and the Solid they have seen is 1.x. For agent-written Solid 2 code, expect these mistakes:
  - one-argument `createEffect`
  - `createResource`, `Suspense` or `ErrorBoundary`
  - `solid-js/web` imports and `classList`
  - reading a signal straight after setting it and expecting the new value
  - React habits such as destructured props or `useState`
  
  The team is clearly aware of this. The package ships a cheatsheet with an explicit warning to AI code generators, SKILL.md files, and coded dev diagnostics with suggested fixes. In practice an agent writing Solid 2 needs that cheatsheet in context, a dev build, and a loop that feeds the diagnostics back to it. With React or plain DOM code the agent's priors are already right.

## 6. For agentbay

**Build step.**
- Solid JSX needs a compiler: Oxc or Babel, through `@solidjs/vite-plugin`. That breaks the kit's no-build rule.
- 2.0 does have a no-build path. `@solidjs/html` (2.0.1) describes itself as tagged-template templating for Solid with no build step. It parses templates at runtime without eval, so it is CSP-safe. Its README says it is somewhat slower than JSX, has a larger runtime that cannot be tree-shaken, and needs reactive expressions wrapped by hand, as in `${() => x()}`. `@solidjs/h` (hyperscript) also exists.
- I ran an `html` counter on 2.0.3 under happy-dom in Node with no compile step. The click updated the button from 0 to 1 after `flush()`.
- One gap remains. A browser page would still need the modules from a CDN or a bundled file, which is a build step for the page, not the kernel. Neither the Long Hold post nor the docs I could reach mention this path.

**(a) Floor-plan sketch: not Solid, now or later.**
- The output is a static picture: rooms as rectangles and polygons, wall moves, dimensions and cost notes. It needs no reactivity.
- The simplest fit is a TypeScript script that turns a plan object into SVG text and writes one self-contained HTML file. It is type-erased Node, has no dependencies, and agents write correct SVG reliably.
- If you later want to drag walls in the browser, add 50 to 100 lines of plain DOM event code, or a small library such as svg.js. A canvas library like Konva only pays off for heavy interaction.
- Solid would pay off only if the sketch became a live editor with many linked values, such as costs recomputed while you drag. Even then, plain JS can do that at this size.

**(b) Cloud dashboard of runs and approval cards: not now, maybe later.**
- This is a list view, a detail view, and approve or reject buttons with live updates. Solid 2's async memos, `Loading`, `isPending`, optimistic actions and SSE `live()` server functions match that shape well.
- The simplest choice today is server-rendered HTML from the Node service, a small script for the buttons, and SSE or polling for updates.
- If you want a component framework that agents write correctly with no setup, React is the safe pick, but it needs a build.
- Solid 2 is the right pick when all of the following are true:
  - 2.0.x has had a few quiet months of patches.
  - A UI kit you would use, such as Kobalte, has a stable 2.0 release.
  - The TanStack packages leave RC.
  - You accept a Vite build for the dashboard only, or the `@solidjs/html` path proves good enough.
  - An agent given the shipped cheatsheet and diagnostics passes a small trial, for example building the approval card list, without falling back to 1.x or React patterns.
