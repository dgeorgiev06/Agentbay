# agentbay: the words we use

One meaning per word. Briefs, plans, code names and reviews use these words and no others for these things. When a new term is needed, it is added here first. Decisions and their reasons are in `docs/adr/`.

## What the owner sees

| Term | Meaning | Do not say |
|---|---|---|
| **Kit** | The agentbay checkout: the kernel, the adapters and the modes that ship with it. | framework folder, repo root |
| **Coordinator** | The owner's own harness session, outside every step, that runs agentbay through its command line and hands each skill step's task to the agent made for it. The block `bay build` writes into `CLAUDE.md` tells it what to do. The adapter's README calls it the main thread. | Chief of Staff, main thread, main agent |
| **Project** | The owner's folder. It holds `agentbay.config.yaml`, the project's own modes and the `.agentbay/` data folder. | workspace, app |
| **Mode** | A folder with a `mode.yaml`. The unit that is installed, composed and permitted. | plugin, component, connector |
| **Action** | A named thing a mode can do, with typed input and output and declared effects. A mode's actions are its interface. | feature, command, endpoint |
| **Step** | One entry in an action's `run` list: a script, a skill or a call. | task (see below) |
| **Script** | Code a step runs, in a confined child process. It reaches the kernel only through the toolbox. | connector code |
| **Skill** | A `SKILL.md` with the seven sections. An agent does the work; the kernel checks the output. | prompt, playbook, role |
| **Workflow** | A named list of workflow steps (action, approval, wait, foreach) that the kernel runs durably. | pipeline, flow |
| **Run** | One execution of an action or workflow, recorded in the kernel database. It can wait, resume and be undone. | job, session |
| **Side by side** (a foreach's items) | Items of one `foreach` that run at the same time, at most its `sideBySide` of them, in one kernel process. Their output stays in item order. A run may then wait on several steps at once, its first under `waiting` and the others under `alsoWaiting`. | in parallel, concurrently (fine in prose), fan-out, matrix |
| **Attempt** (of an item) | One run of a side-by-side foreach's item. A rerun of a failed item is its next attempt, whose steps carry the attempt in their key, as `each[2]~2`; the first attempt's keys carry none. | retry, try |
| **Interface** | A set of action signatures with no code, named `name@major`. A mode implements it; another mode requires it. | API, contract (see below) |
| **Binding** | The project's choice of which mode serves an interface for a requiring mode. | wiring, injection |
| **Brought mode** | A base mode active in a project because forge is: proof, bound to `proof@1`, git-worktrees, bound to `worktrees@1`, and requirements, bound to `requirements@1`, each only while the config binds no mode to that interface. The kernel brings them; forge brings no toolchain, and `bay check` names each mode it brought. | default mode, implicit dependency, auto-install |
| **Effect** | What an action may do to the world: `read`, `write`, `network`, `spend`, `delete`. Declared per action. | permission (see Grant) |
| **Grant** | What a mode may reach: its database, paths, secrets, hosts, commands. Declared in `resources:`. | permission, capability |
| **Throwaway folder** | A folder named under a mode's `resources.files.throwaway`. The kernel makes folders and links in it and removes files and folders from it for that mode; the mode's scripts never read or write its files, and its commands fill it. | scratch, temp folder |
| **List** (a mode's) | The commands a mode lists, each by name with its words and effects, the words its commands start with, and its throwaway folders, taken together. A base mode's list is granted to it; any other mode's list is granted only while the owner trusts it. | allow-list, command list, permissions |
| **Trust** | The owner's statement that one named mode outside the kit's `components/base/` may have its list, bound to that exact list by its hash. A changed list is not trusted until the owner trusts it again. Trust stops a mode's script and an agent inside a run's step from granting commands to themselves; it does not stop an agent that has the owner's shell. | allow-list, permission, approval (an approval is a step of a run) |
| **Trust record** | The file `.agentbay/trust.json`: for each mode the owner trusts, the list as trusted, its hash, when and how the trust was given. The kernel reads it at each load, and no mode may name it. | trust file, trust store, allow-list |
| **Throwaway copy** | The folder a caller makes for a toolchain's check or test, holding a copy of the code, and removes afterwards (the worktrees interface's `copy`). The check or test may write inside it and nowhere else. Its folder is the top of a git repository of its own that holds the commit's files as one commit, with the caller's links present and ignored, so tools list the copy's files as they list a project's; nothing done inside it changes the project's repository. It is not a throwaway folder, which a mode names in its manifest, and not a worktree a builder works in. | scratch copy, temporary copy, sandbox, clone |
| **Card** | Any text the kernel prints for the owner to read before answering with `bay approve`, at most 44 columns wide. The trust card is one card. An approval's card is what an approval shows when a script hands it a title and lines; each line has a mark, words and a source, and the kernel checks every line's source before it shows the card. The command `bay approve` is how the owner answers an approval or a card. | prompt, dialog, approval, summary |
| **Trust card** | The card the owner reads to answer `bay approve --trust <mode>`: the mode and its folder, every command of its list with its resolved words and effects, its throwaway folders, what trust means, and the start of the list's hash; after a change, only what changed, and what stayed in one line. Drawn from the manifest alone, at most 44 columns wide. | trust prompt, trust dialog |
| **Start card** | The card forge's workflows `one-slice` and `rounds` show before a slice is built: the planned slice's title, kind, base, write scope, the slices it comes after, its items, and the bugs: those named, that the planter writes them, or that none will be planted; in `rounds`, a line when the slice names no interface files; every line computed from the slice. In `one-slice`, approving it cuts the slice's worktree and rejecting it fails the run. In `rounds`, its choices are `build`, offered only when the slice names interface files, `build-without-interface`, offered only when it names none, and `stop`, which fails the run. Nothing is cut unless the owner goes ahead. | build prompt, kickoff card |
| **Merge card** | The card forge's workflows `one-slice` and `rounds` show after proof has judged a slice. It leads with the answer: whether merge is offered, and why not. Then each leak; each item with its verdict, a failed or not known one with proof's reason in forge's words and then proof's own sentence, a failed `checks` or `fails-first` one with its failing cases' names and, in `rounds`, each message that quotes no test, and each judgement item as for the owner to judge; what changed and where the work is, the size, and a line for each changed kernel, adapter, kit schema or base mode manifest file; the bugs the planter wrote and each that survived; how many rounds ran and why they ended; a line naming the round the reviewer judged in, before the final proof; and the reviewer's and the builder's judgement as judged lines, each remaining finding with its fix or a line saying the fix quotes a test. In `rounds`, after the items, the practices: how many the reviewer answered each way in its last review and how many a check holds, and each practice it answered not held as a judged line, or that the practices were not judged; and, for a slice with interface files, each one whose hash at the last head differs from its hash at the base. Its choices are merge, send-back, keep and discard; merge is offered only when the builder built the slice, no leak was found, every must item, scope and declared that proof judged passed, no must practice is answered not held, and no interface file changed during the rounds. | review card, pull request, summary |
| **Wave run** | One run of forge's workflow `wave`: one wave of a committed plan, its slices' rounds side by side, at most the setting `sideBySide` at once, each slice's own proof, the combined head proved once, and one merge card. | wave job, batch run |
| **Own proof** (of a slice in a wave) | Proof's judgement of one slice of a wave after its rounds, on the slice whole but for its `checks` items, which the wave proves once on the combined head. A slice whose own proof did not pass is left out of the combined head and keeps its branches. | slice proof, partial proof |
| **Combined head** | The commit a wave run makes by merging, in plan order, each slice that passed its own proof onto the wave's base, on a branch `forge/wave-<n>` of its own. Proof runs the toolchain's checks and the whole test run on it once; when they fail, each slice in it is proved alone with its own checks at its own head, to name the slice that breaks the suite. | wave branch, joined commit, integration commit |
| **Wave start card** | The card a wave run shows before anything is cut: the plan and the wave, each slice in two lines, how many builders work side by side and which slices start first, and the most model calls the wave can take. Its choices are `build` and `stop`. | wave kickoff, build prompt |
| **Wave merge card** | The card a wave run shows after the combined head is proved. It leads with the answer: merge offered for how many of the wave's slices, and those left out, or not and why; then each slice's block, as a merge card's items, practices, interface pins, bugs, leaks and rounds, all computed; then the combined head, its checks, and each slice proved alone. Its choices are `merge`, offered only when every slice in the combined head passed its own proof, merged cleanly, and the checks passed there, and `keep`. | wave review, summary |
| **Approval** | A workflow step that waits for the owner and is bound to the content shown. | gate |
| **Budget** | A limit on a run: items, dollars, tokens, minutes. | quota |
| **Toolbox** | `bay/sdk.ts`. The only kernel file mode code may import. | SDK internals, helpers |
| **Test toolbox** | `tests/test-toolbox.ts`. The only kit file a mode's tests may import besides the toolbox. It opens a project, calls actions, answers skill steps and reads runs, and never hands out the kernel. | mode harness, test helpers |
| **Given step** | A step of a workflow whose output a test hands the kernel in place of running it, through the test toolbox's `runWorkflowPart` or `tests/start-part.ts`. The kernel checks the output against the output schema of the step's action, records the step as done under the key a whole run gives it, and marks it with a `step.given` event. Only the first steps of a workflow, at its top, can be given, and no wait; nothing in `bay` or in the toolbox gives one. | stub, mock, fake output, skipped step |
| **Part** (of a workflow) | What a test starts with `runWorkflowPart`: the given steps and `until`, the step after which the run stops and waits for its owner, starting nothing later. The run's target names the part. | partial run, subset, slice (a slice is build work) |
| **Given schema** | A JSON Schema a script hands the toolbox as a value, not as a file, and checks a value against with `context.schemas.checkAgainst`, by the kernel's own validator. It may refer only to its own parts, so nothing outside it is read, and it has limits on its size and on how far its references unfold. | inline schema, ad-hoc schema, schema value |
| **Shared test** | `<name>/tests/shared.ts` beside an interface: what every mode that implements it must do, through the interface's actions only. Each implementing mode runs it from its own tests. | contract test, conformance suite |
| **Operation** | One thing a script or an agent's tool asks the broker to do, such as `files.read` or `commands.run`. Each has one entry in the broker's table: its request, its result and their guards. | call, request kind, broker method |
| **Ruling** | What an operation's rule returns: the value it allowed, which is all its handler is given, or the refusal. | permission, verdict |
| **Toolchain** | A mode that implements `toolchain@1` for one language: it names the language's files and practices, runs its checks in a checkout, and runs its tests there. | language mode, linter |
| **Verdict** | What a toolchain says of one check or one test run, or what proof says of one item of a definition of done: `passed`, `failed` or `inconclusive`. Inconclusive means nothing is known, and it is never a pass; any part of an item that is inconclusive makes the item inconclusive. | result, status, outcome |
| **Failing case** | One case of a failed test run, as a toolchain names it: its name, the test file it is in, and the first line of the test runner's message for it, at most 200 characters with the cut counted. A test file that did not load is not a case: the toolchain names it apart, under `notLoaded`. | failed test, error |
| **Choice** | One named answer an approval offers. It may have a rule: an earlier step's output that is true or false. The owner's decision names one choice, and later steps read it as the approval's output. | button, option (in prose "option" is fine), verdict |
| **Withheld choice** | A choice whose rule was false when the approval was first shown. It stays on the approval with the reason a script wrote, and the kernel refuses it. The rules are not evaluated again. | disabled, hidden or blocked choice |
| **Mark** (of a card's line) | Where a line of an approval's card came from: `ran`, a command the kernel recorded in this run or in a run one of its skills called; `computed`, a step that ran no skill; `judged`, a skill step the approval quotes, to which the kernel adds the skill and its tier, and for a step in a foreach's item, that item and its foreach. The kernel checks the kind of step a line cites, not whether its words are true. | label, tag, calc, source (the source is what a line cites) |
| **Not set up** | What a checkout or a project is for a check, or for the test run, when it lacks what the toolchain needs to run it, such as an agreed script in `package.json`. The verdict is inconclusive, with a sentence saying what to add, and `describe` lists it under `missing`. | missing tool, unconfigured |
| **Agreed script** | A `package.json` script the typescript mode runs by name: `typecheck`, `lint`, `format:check`, `deadcode` and `test`, which every project needs, and `generate:check`, which only some have. | npm task, target |
| **Requirements file** | One YAML file per job, `docs/requirements/<job>.yaml`: outcomes, each with its conditions; what is left out on purpose; open questions; who asked, who answered, and when. Its form is the interface `requirements@1`'s, and `requirements.check` checks it by script, naming every problem with its line. It names no kind of proof. Forge reads it and nothing else of the PM mode. | PRD, spec, user stories, backlog |
| **Outcome** (of a requirements file) | What a person could see working, in one sentence, with an id `O` and a number. It has at least one condition, and a refused one or a sentence saying why nothing of it can be refused. Not a verdict, and not the kernel's `Outcome<T>`. | feature, story, goal |
| **Condition** (of a requirements file) | One thing a person could do and see under an outcome: given, when, then, with a literal value in then, and its id, the outcome's id, `-C` and a number, never used again once removed. A refused one also says, in after, what a person sees once the refusal is over. | acceptance criterion, test case, scenario |
| **Design** | What forge's workflow `design` makes from a requirements file before any plan: the modules, each with what it hides, what it owns and the interfaces it implements; each interface with its actions, each action with its request and response schema, the conditions it serves and its worked examples. A designer hands it in as data, a script checks it, and on approve it is committed as `docs/designs/<job>/design.yaml` and one schema file for each request and response under `docs/designs/<job>/schemas/`: the interface files later slices build against. | architecture, spec, blueprint |
| **Module** (of a design) | One part of a design with one thing it hides, the tables and files only it reads and writes, and at least one interface it implements. Named for what it does. In this repo a module becomes a feature or a mode. | component, service, package |
| **Worked example** | One example of an action in a design: earlier calls if it needs them, an input, and the exact answer or the exact refusal sentence. Every action has at least one. The test writer and the builder are both given it. | sample, fixture, test case |
| **Light path**, **full path** | The two ways forge writes a design, chosen by the owner on the design's first card. Light: one designer, then a challenger. Full: two designers who write apart, the second given nothing of the first, then a challenger who compares the two and chooses one or merges them. Either path writes the interfaces as schema files. | small work, big work, fast mode |
| **Design card** | The card forge's workflow `design` shows before a design is committed. It leads with which design and which path and whether approve is offered; then each module with what it hides, each interface with one line per action, coverage, what the script checked, the practices held by script and those the challenger answered, and on the full path where the two designs differed. Its choices are `approve`, withheld while the check finds a problem or the challenger answers a practice held by design not held, and `stop`. | design review, sign-off |
| **Plan card** | The card forge's workflow `plan` shows before a plan is committed. It leads with the answer: how many slices in how many waves, the longest chain, and whether approve is offered; then each wave with its slices, each with its module and the conditions it meets, coverage, whether every fixed file is made first, what the script checked, the practices held by the script's rules and those the challenger answered, the findings left after the planner's answer, and what the planner changed. Its choices are `approve`, withheld while the check finds an error or the challenger answers a practice held by a plan not held, and `stop`. | plan review, sign-off |

## What a builder of the kit sees

| Term | Meaning | Do not say |
|---|---|---|
| **Kernel** | The code in `bay/`. It loads modes, enforces grants and effects, and runs runs. It never drives a model. | engine (see below), core |
| **Engine** | The part of the kernel that advances a run step by step. | kernel, runner |
| **Broker** | The part of the kernel every resource request passes through. It applies grants and effects. | gateway, proxy |
| **Harness** | The agent program that does skill work: Claude Code, Codex and others. Named in `adapters/`; the kernel names Claude Code only in its sentences that tell the owner where the hook runs. | runtime, agent |
| **Adapter (harness)** | The code in `adapters/<harness>/` that fits one harness to the kernel. | plugin, integration |
| **Tier** | `fast`, `balanced` or `deep`. A skill step names a tier, or a role that gives one; the project config maps tiers to models. | model |
| **Effort** | How hard a tier's model works on a step: `low`, `medium`, `high`, `xhigh` or `max`. The config's `tiers` sets it with the model; a tier without one runs at the harness's own effort. | reasoning level, thinking budget |
| **Role** | One of a closed set the kit owns, in `bay/roles.ts`: builder, test writer, reviewer, planter, designer, challenger, planner. Each names a tier, and a skill step that names a role in place of a tier runs at the role's tier. A ceiling and standing rules for each role are proposed (`docs/designs/roles/design.md`), and so is the card naming it. It decides no step's reads: who may see what is the step's, in its workflow. | persona, agent type, profile |
| **Ceiling** (of a role, proposed) | The tools and roots a role's agents never get, whatever the step's grants and effects give. It only takes away. | permission, tool profile, sandbox |
| **Standing rules** (of a role, proposed) | The sentences every agent of a role is given in its agent file, said once for the role instead of in each skill. Text only: the ceiling is what is enforced. | system prompt, persona |
| **Feature** | A deep module of the kernel: a folder with one entry file. Only the entry file is imported from outside. Listed in `framework/features.yaml`. | module (ambiguous), layer |
| **Entry file** | The one file of a feature that others may import. Its exports are the feature's interface. | index, barrel |
| **Seam** | A place where behaviour can be swapped without editing the code around it. | hook, extension point |
| **Port** | An interface at a seam to the outside world (files, clock, processes, network). Exists only when two adapters exist. | abstraction, wrapper |
| **Adapter (port)** | A thing that satisfies a port: the real one or the test one. Always say which kind of adapter is meant. | mock, stub, fake (as a type name is fine) |
| **Slice** | One piece of work for one builder: one interface, one capability of the kernel or one mode. It has a name, a kind, a write scope, the slices it comes after with the reason, the interface it builds against if any, and its definition of done; its form is the slice in `proof@1`'s request. | ticket, task, phase |
| **Drop** (a branch) | What the worktrees interface's `drop-branch` does: delete a branch its mode made, merged or not, once no worktree of the mode has it, and answer the commit it pointed at so its work can be found again. A branch that is not there is an answer, not a failure. Not `remove`, which takes a folder. | prune, purge, clean up |
| **Find** (a branch) | What the worktrees interface's `find-branch` does: answer the commit a branch its mode made points at, or that there is no such branch, and change nothing. It reads only a name its mode makes, by the rule `drop-branch` names by, and refuses any other with a sentence. | look up, peek, a drop with the branch as `into` |
| **Leftover branch** | A branch a run that ended early left behind under `forge/`, such as `forge/<slice>-planter`. A later `cut` of the same name is refused with the branch's commit until the branch is dropped or another name is chosen; nothing reuses or moves it. Forge drops a leftover of its own scratch before it cuts again; one that may hold work the owner has not decided on, a slice's builder or tests branch, is named on the next start card with its commit. | stale branch, orphan |
| **Build over** | The start card's go-ahead when an earlier run left branches of the slice or wave that may hold work: forge drops them first and answers each commit, so the work can be found again. Offered in place of `build`, never beside it. | overwrite, reset |
| **Sighting** | What the agentbay hook records when it lets a step agent's `submit` through: the hash of the call's token, and the agent's mode and skill. With `skillSteps.run: with-the-hook`, the default, the kernel takes a skill step's output only against an unused sighting of its token by its step's mode and skill, and uses it up. | hook mark, seen flag |
| **Task** | What the kernel hands a harness for one skill step. Not a piece of build work. | job |
| **Brief** | The seven-section instruction a builder receives for a slice. | prompt |
| **Builder** | An agent that writes a slice. | worker, dev |
| **Test writer** | The agent that writes a slice's tests from its conditions and interface, before any builder works, and hands them in as data, never as files. It never reads the builder's code. | tester, QA agent |
| **Round** | One pass of a slice through the test writer and the builder, ending in one commit that holds the builder's work and the tests, which proof judges, then reviewed. Forge's workflow `rounds` runs at most three; a later round asks only who has something to correct. | iteration, cycle, attempt |
| **Kept tests** | A slice's tests while its rounds run, held by forge in its database partition `kept-tests`, each gzipped and in base64, until the final proof's answer has been filtered against them. | stored tests, hidden tests, vault |
| **Finding** | One thing a reviewer asks to be corrected: for the test writer or the builder, the case's name, the question it fails, and one sentence on the fix. A finding for the builder never quotes a test. | issue, comment, remark |
| **Kept packed** | How the kernel keeps the output of an action's skill when the action says `skillOutput: kept-packed`, and every call made under an action that says `calledOutputs: kept-packed`, its input, output and reason and every step under it: gzipped and in base64 in `.agentbay/kernel.db`, so no line of it is in a file as text, and unpacked only for the script that made the call and the skill's own checks. Not secrecy: code that can read the database can unpack it. | encrypted, hidden, secret |
| **Reviewer** | The agent that checks a slice against its definition of done and attacks it, and answers every practice it holds by id: held, not held with the file, or does not apply. Never the builder. | approver |
| **Must practice** | A practice whose id the project lists in forge's setting `mustPractices`. While the reviewer's last answer says one is not held, the merge card withholds merge. Only the workflow `rounds` reads the list; the design and plan steps treat every practice they hold as must. | blocking rule, required practice |
| **Practices debt** | `framework/practices-debt.yaml`: each practice whose holder is a planned check, generated and held by `tests/practices-debt.test.ts`, which lets it only shrink. | planned list, todo |
| **Planter** | The agent that writes the bugs proof plants in a slice, after its last review, from the builder's code and the slice's conditions, given as text. It never sees the tests; forge's check sends back a bug that changes a file the builder did not change, or that shares a run of 20 characters with the tests. | mutator, bug writer |
| **Designer** | The agent that writes a design from a requirements file and a stance and hands it in as data, never as files. On the full path the second designer is given nothing of the first design. | architect |
| **Challenger** | The agent at tier deep that answers every practice held by design for a design, or every practice held by a plan for a plan, by id, held, not held or does not apply. A design's challenger on the full path chooses one of the two designs or merges them; a plan's challenger gives findings for the planner. A script checks its answer. | design reviewer, plan reviewer, critic |
| **Planner** | The agent at tier balanced that cuts a plan from a committed design and hands it in as data, and answers a challenger's findings once. Another model than the plan's challenger. | architect, scheduler |
| **Fixed file** | A file of a slice that its builder may not change: a test a `fails-first` item names, or an interface file the slice builds against. `forge.waves` refuses a slice that changes another slice's fixed file and does not come after it. | locked file, frozen file |
| **Leak** | Text of a slice's tests that forge's check finds in a builder's work after a build: a line of a test, at least 40 characters that are not spaces once the words both sides were given are out, that also stands in a file the builder changed; or the planted mark in such a file or in the builder's answer. A leak ends the rounds and withholds merge. The check finds copied text; it does not show that a builder never read a test. | copy, contamination, cheating |
| **Planted mark** | 32 random hex characters forge puts as a line at the top of each kept test of one run of a slice, in its partition only. No test file, task or card holds it; a builder's work that holds it is a leak. Not a card line's mark. | watermark, canary, token |
| **Bug injection** | Flipping one line on purpose to see whether a test at the feature's interface fails. | mutation testing (fine as a synonym in prose) |
| **Proof** | The base mode that turns each item of a slice's definition of done into a verdict by script, with no model, behind the interface `proof@1`. It reaches code only by copy, call, remove: a throwaway copy, a toolchain's call in it, and the copy removed. | review, QA, verification mode |
| **Kind of proof** | One of eight ways proof judges an item, each a script: `checks`, `fails-first`, `in-scope`, `as-declared`, `bugs-caught`, `same-output`, `count`, `real-thing`. The set is closed. | check type, rule, assertion |
| **Write scope** | The paths a slice may change, as patterns. Proof fails the slice's item `scope` for any changed path outside it. | allowed files, ownership |
| **Declaration** | What a builder states it will change before its first edit: files, and the action names that modes and interfaces gain, lose or change. Proof compares it with what changed and shows it only as counts. | plan of change, intent, manifest |
| **Judgement item** | An item of a definition of done that names no kind of proof. Proof returns it as it was given; a person or a named model judges it, and every card labels it as judgement. | manual item, soft item, review item |
| **Plan** | A YAML file of the forge mode, under `docs/plans/`: a title and the slices of one piece of work, each with its title, and when cut from a design, the requirements and design it was cut from and for each slice the conditions it meets and its interface files. Forge's workflow `plan` writes one from a committed design; one written by hand has the same form. `forge.waves` works out its table, its waves and its longest chain; nobody edits those by hand. A merged slice stays in its plan. | roadmap, backlog, schedule |
| **Wave** | The slices of a plan that can be built side by side: no order between them, and scopes that share no path. A wave can use one builder per slice. | batch, stage, phase |
| **Longest chain** | The longest run of slices in a plan in which each comes after the one before. A plan takes at least as many waves as its longest chain has slices. | critical path |

## Words with two meanings elsewhere

- **Contract.** Use **interface** for a mode's action signatures, **skill contract** for the seven sections, and **shared types** for `bay/contracts.ts`. Never bare "contract".
- **Module.** In prose about design, and in a design (see Module above), a module is anything with an interface and an implementation. In this repo the unit is a **feature** (kernel) or a **mode** (everything else).
- **Adapter.** Harness adapter or port adapter. Say which.
