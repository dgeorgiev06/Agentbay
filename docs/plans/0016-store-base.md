## What the code does today (verified)

- **An abstract base needs `roles`.** The mode schema requires `purpose`, `features` and `roles` of every mode that does not `extends` (schemas/mode.schema.json:255-266), abstract or not. So `store` needs an env of its own, as the proposal says.
- **That env must be protected, and so must the name.** A protected mode's envs must be protected envs (bay/lint.py:876-878), and an env may write `components/store` only if the mode or connector named `store` is protected (bay/lint.py:901-906). So kernel.yaml gets `store` under `protected.mode` and `store-local: {}` under `protected.env`. The proposal names the first and not the second; both are in kernel.yaml, which it touches. A child that forgets `roles:` then gets a placement gap instead of writing into the base's data folder (`may_place`, bay/boundary.py:158-165).
- **B-11 and `owns:`.** `doc_hits` on today's docs with `store` added finds 16 lines, as the proposal says. A core-owned folder is not an instance name (bay/boundary.py:441-446). But `bay check --base <ref> --docs` reads the map at the merge-base (bay/boundary.py:262-276, 476), so against origin/main the 16 hits stay until this change is merged. See the differences.
- **`needs.optional` is cheap.** `instantiate` already skips an unbound capability, because `connectors_of(None)` is `[]` (bay/connect.py:232-235, bay/model.py:609-614). Only `check_connector` reports it (bay/model.py:672-676). A third reader, the artifact graph (bay/graph.py:243-244), draws the connector's `needs` edges and is not in `touches:`.
- **A store with no source is never stale.** `_stale` compares `canonical(state["selectors"])` with `canonical(settings["selectors"])`, both `[]` when absent (bay/selector.py:184), and the stored sources with `_bound()`, both empty (corpus_store.py:384-399). Two traps: `_selectors()` raises when no selectors are configured (corpus_store.py:484-489), so add, update and delete must not call it; and `_enforce_scope` runs `DELETE FROM items` when no source is bound (corpus_store.py:610-614).
- **The obsolete tests.** `test_feed_briefing_is_complete_after_extends` (tests/test_inheritance.py:26) asserts that feed inherits `sync`, `digest` and `prune`, the base's digest playbook path, config and coordinator playbook. All are false by design afterwards; what stays true is the inherited types, the two shared skills and the ask playbook, which fit `test_child_overrides_review_steps_roles_and_inherits_the_rest` (:46). `test_mail_briefing_extends_briefing_and_places_roles_in_local_mail` (components/mail-briefing/tests/test_mail_briefing.py:43) is not obsolete: only its name, `extends` value and feature set change, and its read-only assertion matters more now. See the differences.
- **The mail golden delta.** The golden stores the `threads` read under the key `threads`, holding `{coverage, threads}` (components/briefing/tests/golden/mail-briefing.json). After the change it holds `{coverage, rows}`. `mail_deltas` (components/briefing/tests/test_offline_golden.py:72-94) is where the one named rename goes. Neither golden contains `items.store` or `briefing`.
- **The guard matrix probably needs no rename.** Its rows are logical (`mode:briefing/...`, `connector:corpus-store/...`); the kit path of each comes from the loader, and moved paths are mapped back (`physical`, `path_deltas`, `undo_move`, tests/test_guard_matrix.py:29-42, 236-300). The shim decision does not read the endpoint name (bay/guard.py:428-438), so the `items.store/v1.query` probe rows decide the same. Decisions are compared before any rename (`changed`, :344-348). After the move, `mode:briefing` probes an absent user folder, which is unprotected before and after.
- **How the limits count today.** `kit_python_lines` sums every `.py` under `components/` and `adapters/` outside a `tests` folder (bay/limits.py:37-38); `tests` counts `def test_` in every file `_TEST_FILE` matches (:21, :47); `bay_lines` counts `bay/` only (:41). I counted the new scope on this branch with `protected_by` from kernel.yaml plus `adapters/`: kit 5066 (gmail-api 992, x-api 263, email 165, post 93 leave), tests 460 (gmail-api 37, x-api 15, mail-briefing 14, improve 11, the two goldens in unprotected components/briefing/tests leave). With `components/store` protected, tests is 462. The proposal's numbers hold.
- **The two-connector order cannot work.** A kind may hold one document per name (bay/model.py:359), so a `components/store/connectors/corpus-store` next to the old one fails the load. Part 2 therefore renames to v2 in place.
- **Other cites hold:** `_apply_extends` (bay/model.py:255-292), `merge_mode` (:378-410), `_feature` reads `md.dir / ep["playbook"]` (:1228), `_settings` (bay/dispatch.py:580-587), `_gate_plan` (:658-668), a gate with no `approves` always runs (:477-480), `_transact` saves DURABLE first (corpus_store.py:431-448), `deleted` is honoured by sync and prune (:885, :970-974), use shims refuse non-read effects at runtime (bay/dispatch.py:267-269).

## Where the plan differs from the proposal

1. **The build order.** The proposal's second commit puts `components/store` next to `components/briefing`, which fails the load: two connectors named corpus-store (bay/model.py:359). The plan renames to v2 in place (part 2), adds behaviour (part 3) and only then moves (part 4).
2. **The builder cannot write most component folders.** framework-dev may write only its `fs.write` list (bay/guard.py:368-371). That list cannot name unprotected components (bay/lint.py:901-906), and components/store joins it only after kernel.yaml changes and a build. So the † edits are made by the coordinator on the main thread with the owner's prompts, and part 4 has a build in the middle. The proposal does not say who writes these files.
3. **`store-local` is a protected env.** It is needed under `protected.env` in kernel.yaml (bay/lint.py:876-878). This is in a touched file; it is a missing detail, not new scope.
4. **B-11 against origin/main stays red until merge.** `--docs` judges the head's docs by the base's map. The evidence for B-11 is `--base HEAD --docs`. The release Result should say this, so the review does not read the 16 hits as a failure.
5. **bay/graph.py.** With `needs.optional`, the graph loses the corpus-store -> items.source edge unless graph.py:243 reads both lists, a 0-line change. Recommended: add `bay/graph.py` to `touches:` before the gate. If not, the edge is lost, and nothing tested depends on it.
6. **The mail tests.** `test_mail_briefing_extends_briefing_...` is not obsolete. The plan renames it and puts the delete flow into `test_offline_sync_digest_and_ask` instead of adding `test_delete_asks_first_and_never_touches_the_source` and merging two tests. The coverage is the same and the test count is honest. The guard-matrix rename is expected to be unnecessary; add it only if the full compare fails, and then only after the decision diff.
7. **Two refusals the proposal left open.** `add` refuses an extId already stored, and a store given no `sourceKinds` refuses every add.

## Risks (security first)

- **The delete gate.** It has no `approves`, so it always runs (bay/dispatch.py:477-480), and it binds nothing but the call. The ids are the call's input and cannot change after the call starts, and the gate shows the preview. A chat approval needs no `--sha` here, so the coordinator's rule "approve only on the owner's words" is the only check on that path, as for every gate without a file. Agents cannot reach `delete`, because the use shim refuses non-read effects at runtime (bay/dispatch.py:267-269). The renamed mail test must still assert that.
- **The never-re-store record.** A sync that runs during a delete would save its own copy of `deleted` and drop the new id, and the message would come back. Delete must hold `_exclusive()` and save `deleted` before the commit. The key is the stored `source:ext_id`, the same string `_store_fetched` compares (corpus_store.py:885). Prune keeps honouring it.
- **The kind guard on add and update.** Without it, an add of `kind: email` would pass as mail in `v_email`, and the citation check accepts any stored id (bay/dispatch.py:591-603). The guard fails closed when `sourceKinds` is missing; `update` refuses any non-local item; `source` and `id` are never taken from the caller. A local item is still citable, which is correct, since you wrote it.
- **Mail stays read-only at the source.** items.source/v1 has only `fetch`, and the Gmail scope is read-only. `delete` must never touch `self.ctx.sources`, and both delete tests assert fake-mail's calls are unchanged.
- **The limits scope must not hide kernel growth.** bay_lines still counts all of `bay/`, and adapters/ and the protected components (corpus-store included) still count. The predicate reads the working tree's kernel.yaml, so this change's swap to `components/store` widens the count. An unreadable map is `closed`, and `protected_by` then marks everything, so the error is on the side of counting. Shrinking the protected list is a kernel.yaml edit, which B-1 and the gate cover. The cost is real, though: growth in gmail-api, x-api, mail-briefing and improve's own tests is now seen only by review.
- **The guard policy changes mid-part.** After step a of part 4, framework-dev may write components/store but not components/briefing's old protected paths. If the build is skipped, step b is denied, which is safe.
- **Sibling drift.** The prune playbook, settings keys and coordinator playbook are copied into both children (owner decision 3).
