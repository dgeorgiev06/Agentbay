## Risks (security first)

- **The guard under construction is the guard in force.** This session's hook runs bay/guard.py from this checkout. Parts 4, 6 and 8 change it while the call is running. A bug that raises denies every subagent call (fail closed); a bug that returns "pass" too early opens writes. Each guard part runs the whole guard test set before its commit, and part 6 is built alone. If subagents are locked out, the main thread can still fix guard.py, because the kit is the project and no deny rule covers it.
- **Plan approvals are as strong as the ledger.** Agents cannot write `.agentbay/`, and while a plan awaits approval the guard denies all Bash but `bay plan`, so a test run cannot forge an approval before the first one. After an approval, a builder may run tests, and test code can append to the ledger (item 9's bypass), so it could forge the approval of a later revision. DESIGN's threat model states this; the review of the whole diff is the control.
- **The plan file write.** Before approval the agent may write exactly `docs/plans/<taskId>.md`. The path is compared after `norm` (realpath), so a symlink at that name resolves to its target and is denied. `never_write` and the env's `fs.write` still apply.
- **Chat channels.** Plan approvals and backlog decisions from chat use the same channel as chat gates: the quote, `--sha` of what was shown, `user@chat-via-cos` in the ledger and Claude Code's prompt. They are on only when `approve.from` lists chat. A prompt-injected coordinator can ask; it cannot pass the prompt.
- **`bay auth` without a terminal.** An injected coordinator could start a login; the owner confirms in the prompt and again in the browser. The login prints only the authorization URL (client id, PKCE challenge, state), and the token goes to the keychain. `bay secret set` keeps its terminal check.
- **The config cutover.** After part 1, every `bay` command that loads the kit fails until the owner edits the config. The error names the fix.
- **The heartbeat is advice, not enforcement.** Another Claude Code session started in the project refreshes `guard.seen`, so a session without the guard can read "active" for up to two minutes. The line only informs; nothing grants or denies by it.
- **B-3 accepts more.** A listed mode folder now covers its feature folders. Protected paths are judged as core (B-1) first, so this does not reach the kernel or the framework's own components.
- **`scope` is conservative.** It does not know B-2 (a new component folder passes the boundary check unlisted), so a plan that creates a new component must list it. Listing more is harmless.
- **Guard cost.** The guard reads and folds the ledger on each subagent tool call. The ledger is append-only and grows; if this becomes slow, a later proposal can index it.
- **Two summaries change.** `call.completed` for a closed call now carries the reason; a reader that matched "abandoned" in the summary should read `data.status` instead, which it already holds.
