- **The gate does not recognise a plan path, and would double it.** `_file_subject` picks from a list only a `PROPOSAL_PATH` match (bay/dispatch.py:430), so `$steps.<id>-plan.artifacts` names no file. `_gate_subject` derives `docs/plans/<stem>.md` from any subject (bay/dispatch.py:421), so a plan subject would carry itself as its own plan and `approve` would demand two sha prefixes. - **No mode author can write an injected-style `approves:`.** mode.schema.json requires `approves` to start with `$in.` (`APPROVES_PATTERN`, bay/workflows.py:53). Only the expansion can produce one that starts with `$steps.`, which lets the dispatcher tell a plan gate apart without a new field.
- **The reopen check fits in `_advance`.** Every submit and approval ends in `_advance` (bay/dispatch.py:343). A passed or skipped gate keeps its subject in `state["gates"][id]["approves"]` (bay/dispatch.py:362). `approve` refuses a call that is not `awaiting-approval` (bay/dispatch.py:156-157). `_public` prints the planning-time `why` (bay/dispatch.py:724-725). One caveat: `submit` stores the output and moves the cursor before it calls `_advance` (bay/dispatch.py:106-109), so the result submitted after an unseen edit is recorded, and the call resumes after it.

## Where the plan differs from the proposal

1. **A missing touch.** `components/forge/envs/framework-dev.yaml` must name `components/tools/envs/plan-writer.yaml`, or lint fails (bay/lint.py:888-900). Add it to `touches:` before the gate.

3. **Validation lives in resolve, not lint.** The `approve.plans` checks are resolve gaps, like every other `agentbay.config.yaml` gap. bay/lint.py is not edited; it may stay in `touches:` or be dropped.

5. **INTERFACES.md headroom is 2 words, not 13.** Part 6 cuts about 11 more.
6. **`--defer` and `--wontfix` keep today's channel.** Read literally, routing every backlog decision through `_approval_channel` would make deferring need a terminal. Only approving follows `approve.from`.
7. **A listed endpoint must declare `write`, and its mode must need both workspace capabilities.** Otherwise resolve reports the planner's effect or tools. This rules out `delivery.research`.

## Risks (security first)

- **The config switch.** From part 1 until the owner edits the file, every `bay` command here fails, including this call's. The coordinator must not edit the file through Bash. The main-thread guard does not stop that (it asks only for `bay` writes, bay/guard.py:139-145). Only the coordinator rule stops it, which the threat model should state as a known gap.
- **What the plan gate binds.** It binds only a `docs/plans/` file the plan step listed. A mode author cannot forge that form of `approves:`, and a planner that lists a proposal or nothing cannot get its gate passed. The planner can still read the whole project, as every role can.
- **The confinement depends on the build.** The planner's write scope exists only in `.agentbay/guard.json`. Until `./bay.sh build` the planner's subagent file does not exist either, so the step cannot run unconfined; it cannot run at all.
- **Backlog decisions from chat.** They exist only when `from` lists chat, they are labelled `user@chat-via-cos` with the quote, and they reach the store only through the `ownerOnly` endpoint. The improve playbook's "never relay one from chat" must change in the same change, or the coordinator follows the old rule.
- **`bay auth` from the app.** An injected coordinator could start a login. The owner confirms twice, at the Claude Code prompt (always asked after part 2 and a build) and in the browser.
- **A reopened gate.** The builder keeps working under the old approval until its next submit, and that submit's output is recorded before the call returns to the gate. Nothing after it runs until the owner approves again. Parts 3 and 4 must keep the subject's shape, or this call returns to its own gate.
